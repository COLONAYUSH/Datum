# Managed RAG platforms: OpenAI file_search / Vector Stores & Azure AI Search

Autopsy date: 2026-08-05. Scope: OpenAI's hosted retrieval stack (vector stores + `file_search` across Assistants → Responses APIs, plus ChatGPT connectors / Deep Research over enterprise data) and Microsoft's Azure AI Search (classic hybrid pipeline, integrated vectorization, semantic ranker, and the 2025+ agentic retrieval / knowledge-base APIs). These are the two dominant "don't build RAG, rent it" offerings; their design choices define what a next-generation framework must beat.

---

## Identity & adoption

### OpenAI vector stores + file_search
- **Maintainer:** OpenAI. Proprietary, closed-source, API-only. No self-hosting.
- **Timeline:** `retrieval` tool (Assistants beta, Nov 2023) → `file_search` v2 with vector stores (April 2024) → **Responses API file_search (March 2025)**, which finally added attribute/metadata filtering and a direct `vector_stores/{id}/search` endpoint ([mamezou-tech write-up](https://developer.mamezou-tech.com/en/blogs/2025/03/19/openai-responses-api-filesearch/)). The **Assistants API is deprecated with a hard shutdown of August 26, 2026**; OpenAI provides *no automated migration of Threads to Conversations* ([migration guide](https://developers.openai.com/api/docs/assistants/migration)).
- **Adoption signal:** default RAG path for the largest developer ecosystem in AI; ChatGPT connectors (June 2025) extended the same managed-retrieval posture to Google Drive, SharePoint, Box, etc. for ChatGPT Team/Enterprise and Deep Research.
- **Pricing:** storage $0.10/GB/day after 1 GB free; $2.50 per 1,000 file_search tool calls (Responses API) ([docs](https://developers.openai.com/api/docs/guides/retrieval); [eesel guide](https://www.eesel.ai/blog/openai-vector-stores)).

### Azure AI Search
- **Maintainer:** Microsoft. Proprietary managed service (né Azure Search 2015 → Azure Cognitive Search → Azure AI Search, Nov 2023). Lucene-derived full-text core with proprietary vector/semantic layers.
- **Timeline:** vector search + semantic ranker GA Nov 2023; integrated vectorization GA ~Nov 2024; **agentic retrieval / knowledge agents public preview May 2025 (Build)**, GA in the `2026-04-01` REST API with newer capabilities still preview-only (`2026-05-01-preview`) ([overview](https://learn.microsoft.com/en-us/azure/search/agentic-retrieval-overview); [InfoQ](https://www.infoq.com/news/2025/05/azure-ai-search-agent-retrieval)). Now underpins **Foundry IQ**, Microsoft's "managed knowledge layer" for agents.
- **Adoption signal:** the default retrieval backend for Azure OpenAI "On Your Data", Copilot-adjacent enterprise RAG, and the widely-forked `azure-search-openai-demo`. Enterprise-heavy user base; Microsoft claims agentic retrieval improves answer relevance "up to 40%" vs single-query RAG (vendor benchmark).
- **Pricing:** dedicated tiers (Basic, S1–S3, L1/L2) billed by Search Units (replicas × partitions); Serverless Developer tier in preview (2026). Semantic ranker and agentic retrieval billed separately (query-based and token-based respectively).

## Retrieval-pipeline architecture

### OpenAI file_search / vector stores

| Stage | How it's modeled | Defaults | Extensibility |
|---|---|---|---|
| Ingestion | Upload file → attach to vector store; auto parse/chunk/embed/index | async; status `in_progress`→`completed` | none beyond chunking params; no connectors at API level; re-upload on change |
| Parsing | opaque, managed | unknown internals | none; docs admit no image/chart/table parsing inside documents; CSV/JSONL "limited support" |
| Chunking | fixed-size token windows | 800 tokens, 400 overlap; configurable 100–4096 / overlap ≤ half | `chunking_strategy` per file only — no semantic/structural chunkers |
| Embedding | fixed | `text-embedding-3-large` at **256 dimensions** | **not replaceable**; embeddings not exportable |
| Indexing | managed vector DB + keyword index | HNSW-like ANN (inferred from recall behavior) | none |
| Query handling | model-driven: query rewriting, decomposition into parallel searches | `rewrite_query` option on direct search | attribute filters (eq/ne/gt/…, and/or) since Mar 2025 |
| Retrieval | hybrid semantic+keyword, RRF via `ranking_options.hybrid_search` (embedding_weight/text_weight) | hybrid on | weights tunable |
| Rerank | managed reranker | `ranker: auto` (or dated snapshots e.g. `default-2024-11-15`), `score_threshold` 0 | choose snapshot + threshold only; model itself opaque |
| Synthesis | up to 20 chunks (4o/o-series) placed into model context with citations | max_num_results ≤ 50 on direct search | prompt-level only |

Limits: 512 MB & 5M tokens per file; 10k files/store (raised to 100M for stores created after Nov 2025); 16 attribute keys per file; 300 req/min per vector store ([retrieval docs](https://developers.openai.com/api/docs/guides/retrieval); [file-search docs](https://developers.openai.com/api/docs/assistants/tools/file-search)).

### Azure AI Search

| Stage | How it's modeled | Defaults | Extensibility |
|---|---|---|---|
| Ingestion | pull-model **indexers** (Blob/ADLS/SQL/Cosmos/OneLake/SharePoint) or push API | scheduled ≥5 min; change detection via LastModified | custom skills (webhooks), push API for full control |
| Parsing | indexer document cracking + **skillsets** (OCR, Document Layout skill, entity skills) | text extraction caps by tier (4M–16M chars/blob) | 30 skills/skillset; custom Web API skills |
| Chunking | **Text Split skill** inside "integrated vectorization"; index projections map one doc → many chunk docs | fixed pages/sentences w/ overlap | custom skill for smarter chunking |
| Embedding | embedding skill → Azure OpenAI (or Foundry model) at index & query time | text-embedding-3-large etc.; user-chosen dims ≤ 4096 | **any embedder** via custom vectorizer/skill — real advantage over OpenAI |
| Indexing | inverted index (BM25) + HNSW (or exhaustive KNN) vector fields; filterable/facetable fields | HNSW params user-set | scoring profiles, analyzers, synonym maps |
| Query handling | classic: single query (text/vector/hybrid + OData `filter`); **agentic**: knowledge base sends query+history to LLM which plans parallel subqueries (reasoning effort minimal/low/medium) | hybrid = RRF fusion | full query DSL; MCP endpoint for agents |
| Retrieval | parallel subquery execution across knowledge sources (indexed or remote e.g. web/SharePoint) | keyword/vector/hybrid per source | knowledge source kinds growing |
| Rerank | **semantic ranker** (Bing-derived cross-encoder): reranks only top-50 L1 results; builds ≤2,048-token summary per doc from configured title/keywords/content fields, trimming overflow | rerankerScore 0–4 | semantic configuration field priority only; model opaque |
| Synthesis | agentic retrieval merges subquery results into unified grounding payload + citations + activity log; optional LLM answer synthesis | merged content always returned | you own the generation step |

Billing for agentic retrieval is double-metered: Azure AI Search bills "retrieval tokens" for subquery execution + semantic reranking, while Azure OpenAI separately bills query-planning/synthesis tokens ([overview](https://learn.microsoft.com/en-us/azure/search/agentic-retrieval-overview)).

## Agentic integration

- **OpenAI:** file_search is a native tool inside the Responses API agent loop — the model decides when to search, decomposes queries, and cites results; zero orchestration code. But it is **only** available inside OpenAI's models (not Chat Completions, not other vendors), and tool invocation is model-mediated and non-deterministic: recurring forum threads document the model skipping the search entirely or over-invoking it and hallucinating "user uploads" ([thread 1210922](https://community.openai.com/t/responses-api-file-search-tool-issues-and-guidance/1210922), [thread 947363](https://community.openai.com/t/file-search-is-not-working-consistently/947363)). ChatGPT connectors + Deep Research extend this to live enterprise sources via (remote) MCP, but governance is thin (see security section).
- **Azure:** agentic retrieval is explicitly designed as a *knowledge tool for agents*: knowledge bases are callable via a `retrieve` action **or an MCP endpoint**, return grounding + citations + an activity log, and support conversation-history-aware query planning. Foundry IQ packages this as a reusable, "permission-aware" knowledge layer. It is agent-*serving*, not agent-*hosting* — your app still owns the loop. Reasoning-effort tiers (minimal/low/medium) trade latency/cost for planning depth; knowledge-source fan-out is capped (3–10 sources per knowledge base depending on effort/API version) ([limits](https://learn.microsoft.com/en-us/azure/search/search-limits-quotas-capacity)).

Neither platform offers agent memory primitives; both treat retrieval as a stateless tool call.

## Strengths (steelman)

1. **Best-practice retrieval by default.** Both ship what most DIY stacks never reach: hybrid keyword+vector with fusion, query rewriting, parallel sub-queries, and a trained cross-encoder reranker — zero config. OpenAI's docs describe automatic query rewriting, decomposition, hybrid search and reranking ([file-search docs](https://developers.openai.com/api/docs/assistants/tools/file-search)); Azure's semantic ranker is a genuine Bing-grade L2 ranker.
2. **It measurably works.** In the independent retrievalci benchmark (81-doc enterprise corpus, 50 stratified questions), **Azure AI Search scored highest of all hosted RAG services (84.0; recall 90.9%)**, with OpenAI file_search at 78.5 ([retrievalci](https://github.com/colon-md/retrievalci); [HN thread 48102521](https://news.ycombinator.com/item?id=48102521)).
3. **Operational outsourcing.** No vector DB to run, no embedding pipeline to babysit; OpenAI storage pricing is trivially cheap for small corpora; Azure gives SLAs, replicas, private endpoints, RBAC, network isolation.
4. **Azure's genuine enterprise depth:** custom embedders, OData filters, scoring profiles, synonym maps, 100+ data-source indexers, document-level security patterns, and now an MCP-native agentic retrieval API with an auditable activity log.
5. **Fast innovation absorption:** metadata filtering, hybrid tuning knobs, ranker snapshots (OpenAI); agentic multi-query planning GA'd within ~a year of preview (Azure). Managed platforms retro-fit research advances to all tenants at once.

## Issues & failure modes

### abstraction-design

- **[OpenAI] Full-stack black box: fixed embedder, opaque parser, unexportable index.** Embeddings are locked to text-embedding-3-large @256 dims; you cannot swap embedding models, inspect parsing, tune ANN parameters, or export embeddings to migrate — "can't just swap in a cheaper embedding model, switch to a different vector database... or easily migrate to another LLM provider." Evidence: [OpenAI docs](https://developers.openai.com/api/docs/assistants/tools/file-search) (fixed 256-dim embedder), [eesel critique](https://www.eesel.ai/blog/openai-vector-stores). **Severity: major. Label: documented-recurring.**
- **[OpenAI] Ranker opacity:** reranker is selected via `ranker: auto` with undocumented dated snapshots; when relevance shifts (as in the Sept 2025 incident) users cannot debug because no stage of parse→chunk→embed→rank is observable. Evidence: [retrieval docs](https://developers.openai.com/api/docs/guides/retrieval) + [status incident](https://status.openai.com/incidents/01K4V50KXFRFE3DGMZH4GK3QM0). **Severity: major. Label: architectural-inference.**
- **[Azure] Semantic ranker silently truncates and only sees top-50.** Reranking applies solely to the top 50 L1 results; each doc is compressed to a ≤2,048-token summary assembled from configured fields, and "the system ignores anything after the maximum limit"; docs also warn `@search.rerankerScore` distributions drift with infrastructure conditions and model updates, breaking fixed thresholds. Evidence: [semantic ranker docs](https://learn.microsoft.com/en-us/azure/search/semantic-search-overview). **Severity: major. Label: documented-recurring (documented behavior + drift warning).**

### retrieval-quality

- **[OpenAI] Severe ANN recall bug: correct chunk only surfaces at top_k ≥ 45.** A chunk with the *highest* similarity score (0.8838) was absent from results for `max_num_results` 2–44 and appeared at rank 1 only at ≥45 — consistent with an under-provisioned `ef_search` in HNSW. Evidence: [community bug 1381267](https://community.openai.com/t/vector-store-search-correct-chunk-only-retrieved-at-top-k-45/1381267) (May 2026, no staff response visible). **Severity: critical. Label: single-anecdote (but mechanistically damning).**
- **[Both] Hosted RAG never abstains.** retrievalci found **all four hosted services (incl. Azure AI Search and OpenAI file_search) hallucinated on every unanswerable question — 0/5 abstention correctness**; precision was mediocre (OpenAI 53.4%, Azure 67.8%). Evidence: [retrievalci](https://github.com/colon-md/retrievalci), [HN 48102521](https://news.ycombinator.com/item?id=48102521). **Severity: major. Label: single-anecdote (one benchmark, but across all vendors).**
- **[OpenAI] Non-deterministic tool invocation degrades effective recall.** Assistants/Responses models skip file_search after the first query, fail on non-gpt-4o models, or answer without consulting files; the standard "fix" is prompt begging. Evidence: [thread 947363](https://community.openai.com/t/file-search-is-not-working-consistently/947363), [thread 1066585](https://community.openai.com/t/file-search-does-not-work-well/1066585), [thread 1041727](https://community.openai.com/t/file-search-tool-broken-assistants-api/1041727). **Severity: major. Label: documented-recurring.**
- **[Azure] Hybrid search returns documents that match neither the text query nor expectations.** Because vector search always returns k results regardless of relevance, RRF fusion can surface semantically-adjacent non-matches past strict text patterns; hard `filter` clauses are the only reliable constraint. Evidence: [jakobs.dev gotcha post](https://jakobs.dev/showcase-azure-ai-hybrid-search-unexpected-results-gotcha/). **Severity: minor. Label: single-anecdote (inherent to k-NN + RRF design).**

### data-processing

- **[OpenAI] Naive fixed-size chunking loses structure.** Only fixed token-window chunking exists; docs themselves list "limited support" for CSV/JSONL and **no parsing of images/charts/tables inside documents**; practitioners report answers spanning page breaks getting split so "neither chunk contain[ed] enough context on its own." Evidence: [file-search docs limitations](https://developers.openai.com/api/docs/assistants/tools/file-search), [Team400 field notes](https://team400.ai/blog/2026-04-openai-file-search-vector-stores-responses-api). **Severity: major. Label: documented-recurring.**
- **[OpenAI] Metadata filtering shipped a year late.** Assistants file_search (Apr 2024) had "no support for custom metadata / deterministic pre-search filtering" — a top forum ask — until the Responses API added attribute filters in March 2025; Assistants users must migrate to get it. Evidence: [file-search docs known limitations](https://developers.openai.com/api/docs/assistants/tools/file-search), [mamezou-tech](https://developer.mamezou-tech.com/en/blogs/2025/03/19/openai-responses-api-filesearch/). **Severity: minor (now fixed). Label: documented-recurring.**
- **[Azure] Indexer ceilings silently cap large documents:** blob-size limits by tier (16 MB Basic → 256 MB S2+) and extracted-character caps (512K Basic → 16M S3) mean oversized docs are partially indexed; indexer max run time is 2 hours in the public multitenant environment, forcing schedule-resume choreography for big corpora. Evidence: [service limits](https://learn.microsoft.com/en-us/azure/search/search-limits-quotas-capacity). **Severity: minor. Label: documented-recurring (documented constraints, frequent forum trips).**

### evaluation-observability

- **[OpenAI] No eval loop, no retrieval telemetry.** No built-in way to test relevance before production, no per-stage traces; third-party guides call out that it "lacks straightforward methods to assess RAG system accuracy on real questions." When OpenAI degraded its own retrieval quality (below), customers had no signal except worse answers. Evidence: [eesel](https://www.eesel.ai/blog/openai-vector-stores); [status incident](https://status.openai.com/incidents/01K4V50KXFRFE3DGMZH4GK3QM0). **Severity: major. Label: documented-recurring.**
- **[Azure] Agentic retrieval costs and behavior are hard to reconstruct.** Docs concede that from the activity log, "precise reconstruction of a query or response isn't guaranteed," and cost estimation requires modeling subquery fan-out × chunk tokens × reranking tokens by hand. No built-in relevance evaluation exists either. Evidence: [agentic retrieval overview](https://learn.microsoft.com/en-us/azure/search/agentic-retrieval-overview). **Severity: minor. Label: documented-recurring (vendor-documented).**

### production-ops

- **[OpenAI] Multi-day platform-wide retrieval-quality regression.** Sept 10–16, 2025: files added during a ~21-hour window were mis-indexed, degrading retrieval quality across Assistants/Responses/Retrieval APIs for ~6 days; remediation required customers to **remove and re-add files** themselves. Evidence: [OpenAI status incident 01K4V50K...](https://status.openai.com/incidents/01K4V50KXFRFE3DGMZH4GK3QM0). **Severity: critical. Label: documented-recurring (official postmortem + forum echo).**
- **[OpenAI] Indexing reliability: files stuck `in_progress` for days/weeks, dashboard/API state mismatch.** A 39.8 MB file uploaded Oct 30 was still "processing" a week later; dashboard showed 0 files while API listed in-progress files; community workaround is delete-and-reupload. Evidence: [thread 1365372](https://community.openai.com/t/vector-indexing-takes-forever-and-vector-stores-files-list-returns-incorrect-results/1365372) plus related threads. **Severity: major. Label: documented-recurring.**
- **[OpenAI] No incremental sync:** vector stores don't watch sources; any change to a Zendesk/Confluence/Drive doc requires custom pipelines to re-upload — the "managed" service still needs an unmanaged ingestion layer. Evidence: [eesel](https://www.eesel.ai/blog/openai-vector-stores). **Severity: major. Label: documented-recurring.**
- **[Azure] Deletion detection is opt-in, must precede the first indexer run, and doesn't work for chunked (one-to-many) indexes.** Indexers never track deletions; you must configure soft-delete policies *before* the initial run or orphans persist ("create a new index using a new indexer"); and "neither native blob soft delete nor soft delete via custom metadata applies when using one-to-many indexing scenarios" — i.e., precisely the chunk-per-document projection every RAG index uses, forcing manual chunk deletion via the REST API. Evidence: [changed/deleted blobs docs](https://learn.microsoft.com/en-us/azure/search/search-how-to-index-azure-blob-changed-deleted). **Severity: critical (stale/orphaned chunks in production RAG). Label: documented-recurring.**
- **[Azure] Capacity is creation-date and region lottery.** Storage/vector quotas per partition depend on when and where the service was created (Basic: 2 GB pre-Apr-2024 vs 15 GB after; vector quota 0.5 GB → 5 GB); several regions permanently retain old low limits; getting new limits historically meant recreating the service and reindexing everything (a partial in-place "upgrade" path arrived only in 2025). Evidence: [service limits & upgrade notes](https://learn.microsoft.com/en-us/azure/search/search-limits-quotas-capacity). **Severity: major. Label: documented-recurring.**

### security-governance

- **[OpenAI] No document ACLs in vector stores.** Attributes are filter hints, not security boundaries; multi-tenant isolation requires one store per tenant/permission-scope and app-enforced routing. Evidence: [retrieval docs](https://developers.openai.com/api/docs/guides/retrieval) (16 attribute keys, no principal model). **Severity: major. Label: architectural-inference.**
- **[OpenAI] ChatGPT connectors: zero-click prompt-injection exfiltration ("AgentFlayer").** Zenity demonstrated at Black Hat USA 2025 that a single poisoned document shared into a victim's Google Drive could make ChatGPT (with the Drive connector) search out API keys and exfiltrate them via image-markdown rendering — no user click required; OpenAI's `url_safe` mitigations were shown bypassable. Evidence: Zenity Labs AgentFlayer disclosure, Black Hat USA 2025; widely covered (e.g., The Hacker News, Aug 2025). **Severity: critical. Label: documented-recurring (multiple outlets + vendor mitigation).**
- **[Both] Connector/tool surface drifts without re-consent.** PromptArmor tracked 2,517 Claude/ChatGPT connectors for six weeks: changes every ~9 minutes on aggregate; 37% of connectors changed; 21 read-only connectors gained write/delete; 283 began injecting custom instructions into model context — "rarely with any notification or re-consent process." Evidence: [PromptArmor, July 2026](https://www.promptarmor.com/resources/claude-and-gpt-connectors-change-every-9-minutes). **Severity: major. Label: documented-recurring.**
- **[Azure] (steelman-side note)** Azure is materially stronger here — RBAC, private endpoints, permission-aware Foundry IQ knowledge sources — but its preview terms warn data "might result in data processing or storage outside of the Azure compliance boundary" when remote/third-party knowledge sources are used ([agentic retrieval overview](https://learn.microsoft.com/en-us/azure/search/agentic-retrieval-overview)). **Severity: minor. Label: documented-recurring (vendor-documented).**

### dx-docs

- **[OpenAI] API churn with hard deprecations.** Responses v2 rollout broke `file_search`/`tool_resources`/`vector_store_ids` parameters sequentially while docs lagged behavior ([thread 1354202](https://community.openai.com/t/breaking-changes-in-openai-api-responses-v2-vector-store-file-search-instability/1354202), Aug 2025); Assistants API shuts down Aug 26, 2026 with no automated thread migration and (initially) lost in-text citation annotations in Responses file_search ([migration guide](https://developers.openai.com/api/docs/assistants/migration); [mamezou-tech](https://developer.mamezou-tech.com/en/blogs/2025/03/19/openai-responses-api-filesearch/)). HN: "I wish OpenAI would provide more clarity about the Assistants API deprecation" ([HN 44052424](https://news.ycombinator.com/item?id=44052424)). **Severity: major. Label: documented-recurring.**
- **[Azure] Preview-API sprawl and rename churn.** Three product names in a decade; agentic retrieval spread across `2025-05-01-preview` → `2025-08-01-preview` → `2026-05-01-preview` with different knowledge-source limits per API version and a dedicated migration doc; portal remains preview-only for some GA features. Evidence: [agentic retrieval overview + limits](https://learn.microsoft.com/en-us/azure/search/agentic-retrieval-overview). **Severity: minor. Label: documented-recurring.**

### performance-cost

- **[OpenAI] Slowest hosted retrieval measured:** p50 retrieval latency ~1,358 ms vs ~400 ms for Azure/Bedrock/Vertex ([retrievalci](https://github.com/colon-md/retrievalci)); forum threads on slow vector search and multi-second file_search round-trips corroborate ([thread 1369742](https://community.openai.com/t/vector-search-results-are-too-slow/1369742)). Storage cost is on *processed* data (chunks+embeddings), which "can be much larger" than source files, making bills hard to forecast ([eesel](https://www.eesel.ai/blog/openai-vector-stores)). **Severity: major. Label: documented-recurring.**
- **[Azure] Agentic retrieval double-billing & fan-out cost blow-up.** Every agentic query = LLM planning tokens (AOAI bill) + reranking-token billing on ~subqueries × 50 chunks × ~500 tokens (Search bill) + optional synthesis tokens; Microsoft's own worked example reranks 150M tokens for 2,000 queries. Latency is also explicitly worse than single-query ("adds latency compared to a single-query pipeline"); practitioners recommend classic RAG "for production stability today" ([overview](https://learn.microsoft.com/en-us/azure/search/agentic-retrieval-overview); [Bob Code deep dive](https://medium.com/@codebob75/azure-agentic-retrieval-a-deep-dive-into-rag-with-ai-search-and-foundry-1f6318d031a2)). **Severity: major. Label: documented-recurring (vendor-documented + practitioner).**
- **[Azure] SU model couples storage, QPS, and HA:** replicas×partitions pricing forces paying for storage growth to get query throughput (and ≥2–3 replicas for any SLA), a recurring cost complaint versus consumption-priced vector DBs. Evidence: [limits/SLA docs](https://learn.microsoft.com/en-us/azure/search/search-limits-quotas-capacity). **Severity: minor. Label: architectural-inference.**

### agentic-integration

- **[OpenAI] Retrieval welded to one vendor's agent loop.** file_search cannot be called from Chat Completions or non-OpenAI models; the *model* is the only orchestrator, so failures (skipped searches, phantom "user uploads") are unfixable at the framework layer. Evidence: [mamezou-tech](https://developer.mamezou-tech.com/en/blogs/2025/03/19/openai-responses-api-filesearch/); [thread 1210922](https://community.openai.com/t/responses-api-file-search-tool-issues-and-guidance/1210922). **Severity: major. Label: documented-recurring.**
- **[Azure] LLM query planning is non-deterministic and capped.** Decomposition quality depends on the assigned model (only gpt-4o/4.1/5-series supported); knowledge-source fan-out is limited to 3–10 sources per knowledge base depending on reasoning effort; planning can miss relevant angles with no feedback loop. Evidence: [retrieval how-to](https://learn.microsoft.com/en-us/azure/search/agentic-retrieval-how-to-retrieve); [limits](https://learn.microsoft.com/en-us/azure/search/search-limits-quotas-capacity); [Bob Code](https://medium.com/@codebob75/azure-agentic-retrieval-a-deep-dive-into-rag-with-ai-search-and-foundry-1f6318d031a2). **Severity: minor. Label: architectural-inference.**

## Community sentiment over time

- **2024 (OpenAI):** enthusiasm for file_search v2's simplicity, quickly tempered by "file search totally broken" / "not working consistently" threads ([922154](https://community.openai.com/t/file-search-totally-broken/922154), [947363](https://community.openai.com/t/file-search-is-not-working-consistently/947363)) and the missing-metadata-filtering gap.
- **2025 (OpenAI):** Responses API praised for filters + direct search endpoint, but the year was dominated by migration anxiety (Assistants deprecation), Responses-v2 breaking-change complaints (Aug), and the Sept retrieval-quality incident. Sentiment: "is this viable for production?" recurs verbatim on the forum.
- **2026 (OpenAI):** infrastructure-grade bugs still surfacing (top_k≥45 recall bug, May 2026; week-long indexing stalls) with little visible staff engagement; serious builders increasingly treat file_search as a prototype tool and graduate to owned pipelines (Team400, eesel guidance).
- **2023–2024 (Azure):** vector search GA received well; grumbling centered on cost, tiny early vector quotas (0.5–1 GB/partition), and tier-recreation pain; the Apr/May 2024 capacity increases ("up to 11x… no price change") were a direct response.
- **2025–2026 (Azure):** agentic retrieval generated genuine excitement (Build 2025, InfoQ coverage) and Azure topped independent hosted-RAG benchmarking; skepticism focuses on preview churn, token-billing opacity, and added latency — practitioners advise classic hybrid+semantic for production while agentic matures. Microsoft's repositioning of Search under "Foundry IQ" reads to some as another rename cycle.

## Benchmarks & third-party evaluations

- **retrievalci / EnterpriseRAG-Bench v1.0.0 (Jan–Feb 2026):** 81 docs, 50 stratified questions, retrieve-only scoring (0.7·recall + 0.3·precision): Azure AI Search 84.0 (R 90.9 / P 67.8 / p50 408 ms); Vertex RAG Engine 82.6; Bedrock KB 82.5; OpenAI File Search 78.5 (R 89.3 / P 53.4 / **p50 1,358 ms**). All four hallucinated on 100% of unanswerable questions. ([repo](https://github.com/colon-md/retrievalci), [HN 48102521](https://news.ycombinator.com/item?id=48102521))
- **Microsoft internal (May 2025):** agentic retrieval "up to 40%" better answer relevance vs single-shot RAG — vendor-reported, methodology not independently reproduced ([InfoQ](https://www.infoq.com/news/2025/05/azure-ai-search-agent-retrieval)).
- **Vendor-comparison blogs** (e.g., [Manticore vs Azure AI Search, Mar 2026](https://manticoresearch.com/blog/azure-ai-search-vs-manticore/)) consistently target Azure's price-per-QPS as the weak flank rather than relevance.
- Gap worth noting for the paper: **neither vendor publishes recall/precision numbers for its own managed retrieval**, and no public benchmark measures OpenAI's chunking/parsing quality in isolation — eval opacity is itself a finding.

## Lessons for a next-generation framework

1. **Observable-by-construction retrieval.** The worst failures here (Sept 2025 silent quality regression; top_k recall bug; semantic-ranker truncation) were invisible to users. Every stage — parse, chunk, embed, index, plan, rank — must emit inspectable artifacts and per-stage metrics.
2. **Abstention is a first-class retrieval outcome.** 0/5 abstention across all four managed platforms shows "always return top-k and generate" is the industry default; a next-gen framework needs calibrated no-answer detection wired through retrieval → synthesis.
3. **Sync/lifecycle is the real product.** Both platforms punt on freshness: OpenAI has no source sync at all; Azure's deletion detection breaks precisely in the chunked one-to-many case. Incremental, deletion-aware, chunk-level sync should be core, not a footnote.
4. **Pluggable embedders and exportable indexes** to avoid OpenAI-style lock-in; portability (dump chunks+vectors+metadata) is a trust feature.
5. **Deterministic control plane, probabilistic assist.** Model-mediated tool invocation (OpenAI) and LLM query planning (Azure) both fail non-deterministically; the framework should let developers force retrieval, pin plans, and replay them (Azure's activity log is directionally right but "precise reconstruction isn't guaranteed").
6. **Security as retrieval semantics:** document/chunk ACL enforcement at query time (Azure/Foundry IQ direction), injection-hardened connector content (AgentFlayer), and change-controlled tool surfaces (PromptArmor drift findings).
7. **Cost legibility:** token-metered multi-query retrieval needs per-query cost tracing and budget caps; Azure's own docs require a spreadsheet to estimate a single query's cost.
8. **Structure-aware ingestion by default** (tables, images, cross-page answers) — the most-cited quality complaint on the OpenAI side is fixed-window chunking destroying document structure.
