# Datum — a retrieval substrate for the agentic era

*The definitive framework specification. Synthesized from five independently-scored architectural stances (`design/proposal-{agent-native,evidence-first,learned-policy,memory-os,systems-db}.md`) against the verified failure taxonomy (`research/03-synthesis/common-issues.md`, CI-01…CI-27) and a three-lens judge panel. Method, scores, graft ledger, and rejected grafts: `design/judgment.md`. Package name throughout: `datum`.*

---

## Abstract

Nineteen years of RAG frameworks re-discovered, piecemeal, a problem relational databases solved in the 1970s: a signature — `retrieve(query, k) → docs` — that is simultaneously the logical request and the physical execution plan cannot express a principal, a budget, a trust tier, or a calibrated evidence-state. All four get smuggled through the one structured input that exists, the metadata filter, which is why a relevance bug and a tenant-isolation breach are, empirically, the same line of code in four independent codebases. Datum separates the two. A small, semver-frozen kernel of typed verbs — `search`, `fetch`, `navigate`, `explain`, `since` — compiles into a plan over a canonical, bitemporal, cryptographically-erasable corpus, executed by conformance-gated physical operators whose *selection* is itself a versioned, safely-promotable policy rather than a frozen heuristic or an unbuilt cost-based optimizer. Every plan is explainable before it runs and replayable by record — not recomputed — after. A grep-shaped, out-of-band evidentiary envelope keeps authority, trust, and provenance metadata server-side, raising the cost of a content-innocent attack class no content-inspection defense fully closes (and this document does not claim otherwise — see §Evidence & trust). A shared transactional write path — one algebra, source-specific policies — lets documents and agent memory coexist without merging their write disciplines. Authorization defaults to physical partitioning where entitlement cardinality is low and to conformance-tested predicates where it isn't, with low-privilege recall measured continuously on whichever path is active. Synthesizing five architectural stances scored against 27 adversarially-verified framework defects, Datum argues the field's gap was never a smarter retriever — it was a missing systems substrate underneath one, buildable today, mostly from database and systems discipline the ecosystem skipped. Almost none of the individual mechanisms below are new — System R's logical/physical split, off-policy replay, bitemporal write algebras, content-defined chunking, and out-of-band provenance channels all have named precedents this document credits throughout, several of them (LOTUS, Palimpzest) closer to this design's own central claim than the source proposal's literature review found. What this document argues is novel is narrower and, we think, still real: which four of RAG's specific, adversarially-confirmed defects collapse into that one split, and a consistent, end-to-end assembly of that substrate for retrieval specifically rather than general AI-data workloads.

## Design axioms

Datum's skeleton is the **systems-db** stance (`proposal-systems-db.md`, "Strata — Retrieval as a Data-Systems Problem"): every mainstream framework's `VectorStore.similarity_search()` *is* the physical plan, one method with dozens of independent per-backend reimplementations of filter translation and score semantics; separating the logical layer (what evidence, under what policy and budget) from the physical layer (which operators, in what order, at what cost) the way System R separated SQL from access paths removes an entire defect class rather than patching it four times. The nine axioms below are that skeleton's own eight, with axiom 9 and internal amendments grafted from the four losing stances where a judge-mandated or independently-stronger mechanism composed without breaking the split.

1. **A retrieval call is a compiled plan, not a hand-wired physical path.** Logical intent (what evidence, under what policy and budget) compiles to a physical plan (which operators, in what order, at what cost) against live statistics — never a single Python method per backend. → **CI-03**.
2. **Every derived artifact is a versioned materialized view over a canonical, content-addressed source — never a primary artifact.** Chunks, embeddings, graph edges, summaries, and caches are all such views, sharing one lineage semantic. → **CI-07**.
3. **Corpus and memory mutation are transactional; every downstream view is incrementally maintained; one typed write algebra serves both, through source-specific policies.** A WAL-committed transaction log is the *only* write path; full rebuild is a degenerate case of incremental view maintenance (replay the whole log), not a separate fragile code path. Documents and conversational memory need different write *policies* — parse/supersede vs. extract/consolidate — but not different write *mechanisms* (grafted from **memory-os**; §Memory & mutation resolves why this doesn't re-merge what the convergence evidence says should stay separate). → **CI-06**, with CI-12's transactional-write leg as an unforced secondary beneficiary.
4. **Principal, policy, and budget are non-optional, typed inputs to plan compilation — never smuggled through a metadata filter.** The same missing slot is why a relevance bug and a tenant-isolation bug are one code path with opposite required failure semantics (degrade gracefully vs. fail closed). → **CI-05** (and CI-09).
5. **Every evidence item is typed, provenance-carrying, and conflict-aware; "insufficient" and "conflicting" are compilable plan outcomes, not generation-time surprises.** A plan that can terminate in `insufficient_evidence` or `conflicted` is a different type signature, not a UX feature bolted on after the fact (evidence-first's conflict-surfacing folded into systems-db's own EvidenceState type). → **CI-10**, CI-04's cheap-now half.
6. **Every plan is EXPLAIN-able before it runs and REPLAY-able after — by re-rendering the recorded trace, not by recomputing against a live, possibly-adaptive substrate.** "Replay" means replay-**by-record**: the persisted trace *is* the artifact, matching evidence-first's Ledger design and Microsoft's own admission that precise reconstruction against a live, identity-predicated, mutating corpus is not guaranteed in principle. This is the mechanism that lets axiom 7's adaptivity coexist with reproducibility (§Resolving the five stance conflicts, #1). → **CI-11**, CI-25.
7. **Physical operators — and the plan-selection policy itself — are pluggable, conformance-gated, and safely improvable.** Nothing ships without passing a mandatory suite; nothing is *promoted* into the default without clearing a debiased statistical gate on this deployment's own traffic (learned-policy's measure→gate→promote→rollback discipline grafted directly onto systems-db's own admittedly heuristic-at-v1 Optimizer). → **CI-03** (again), CI-14, CI-15's self-collision guarded against explicitly.
8. **A small, semver-stable, mechanically-enforced kernel is the only thing a trained policy — frontier or weak, prompted or RL'd — is ever asked to trust.** Two symmetric consumers share it without a scaffolding tax on one or a security tax on the other (agent-native's dual-consumer design grafted onto systems-db's four-verb surface). → **CI-08**, CI-24.
9. **Forgetting is a cryptographic guarantee at the key layer, not a best-effort index operation; authorization defaults to physical partitioning where entitlement cardinality is low and to conformance-tested predicates where it isn't**, with low-privilege recall measured continuously on whichever path is live (memory-os's two headline mechanisms, bounded — §Security & governance). → **CI-06** (the erasure half), CI-05 (the residual).

### Why this skeleton, stated once

`common-issues.md`'s adversarial verification confirmed exactly four of the top twelve issues at high confidence: **CI-03** (filter-channel-is-ACL-channel), **CI-05** (authorization as a paid tier), **CI-07** (ingest-time one-way doors), **CI-08** (churn/demotion/death). Axioms 1 and 7 map onto CI-03, axiom 4 onto CI-05, axiom 2 (and 3) onto CI-07, axiom 8 onto CI-08 — a 1:1 correspondence between the skeleton's own four founding axioms and the taxonomy's four best-evidenced defects, which is the sharpest single argument for choosing this stance as the organizing idea rather than a post-hoc justification for it. No other stance's axiom set lines up this cleanly against the confirmed (as opposed to weakened-and-restated) subset of the taxonomy.

**A correction owed before the rest of this section: the System-R split itself is not undemonstrated territory.** The systems-db proposal's own literature review, and this document inheriting it, never surveyed the declarative-optimizer-over-unstructured-data line of work: LOTUS (Stanford/Berkeley, `github.com/stanford-futuredata/lotus`) and Palimpzest (MIT CSAIL, arXiv:2405.14696) already ship a declarative logical layer over structured-plus-unstructured data with a real logical/physical optimizer that explores plan space and picks execution strategies on cost/latency/quality trade-offs — scoped to general AI-data workloads, not RAG-with-ACL specifically, but close enough to this section's own central framing that it should have been the first thing checked against, not found afterward. What survives this correction is narrower than the original framing claimed: the *diagnostic* move — that four specific, adversarially-confirmed CI defects (CI-03, CI-05, CI-07, CI-08) collapse to one missing primitive — is real synthesis work this document stands behind; the *mechanism* that closes them (split a logical intent from a cost-evaluated physical plan) is not something Datum originates, it is a database-systems idea from the 1970s that a live, adjacent 2024-2026 OSS lineage has already brought partway into the AI-data-workload world. Datum's residual claim is the specialization: typed `principal`/`policy`/`budget` as non-optional compile inputs, fail-closed-by-type ACL predicates, and a plan IR whose outcomes include `insufficient_evidence`/`conflicted` — none of which LOTUS or Palimpzest, built for a different problem (general tabular+unstructured data pipelines, not retrieval-under-ACL for an agent loop), are trying to solve. Every "Solved" or "novel" claim below should be read against this correction, not as if the ground it stands on were previously empty.

**What this skeleton is emphatically not, and the single most important framing correction this document makes relative to its source proposal:** the thesis is the logical/physical **plan separation**, not the cost-based optimizer that sits inside it. All three judge lenses independently flagged the systems-db proposal's own cost-based Optimizer as its weakest point — "a rule table wearing an optimizer's costume," a "multi-year systems-research undertaking" for the *general*, cross-operator (BM25 + ANN + graph + SQL-predicate, arbitrary budget dimensions) case. The proposal's own stronger version of that line — "unsolved even for filtered ANN alone" — does not survive this revision's own citation check: arXiv:2602.17914 ("Efficient Filtered-ANN via Learning-based Query Planning," Feb 2026, already cited in this project's own `research/01-landscape/indexing-vector-databases.md`) reports exactly a learned per-query plan selector for filtered ANN with measured recall/speed trade-offs — a narrow slice of "cost-based plan selection" that is, in fact, built. The defensible claim is narrower and survives: a *general*, cross-operator cost-based optimizer — one that trades off BM25 against ANN against graph traversal against an LLM-mediated enrichment step, on a shared cost vector, at production latency — remains unbuilt and is a multi-year undertaking; single-operator slices of that problem (filtered ANN specifically) are being solved piecemeal, in public, right now. Datum's answer is architectural, not aspirational, and does not depend on either version of the claim: **plan-selection is one more registered policy occupying a slot in the plan compiler.** v1 ships a declared, dated, benchmarked rule-table policy in that slot (exactly what CI-14 asks for); axiom 7's grafted promotion-gate machinery is what lets that table improve, safely and continuously, on a given deployment's own traffic — instead of either freezing forever (CI-14's disease) or requiring a research breakthrough to ship at all. The Plan IR, the EXPLAIN/REPLAY contract, the conformance requirements on physical operators, and the WAL/lineage substrate are all fully buildable today with zero dependency on that research maturing. Demoting the optimizer to a slot is also how Datum honors the dissenting staff-engineer lens without switching skeletons: that lens's objection to systems-db was "no unproven crown-jewel dependency" scored *against* agent-native's favor — removing the crown-jewel dependency from the winning skeleton answers the objection directly rather than arguing past it. The slot-based framing is also, on its own terms, not a new abstraction: Palimpzest's optimizer already picks among concrete logical/physical programs by estimated cost/time/quality at runtime, arXiv:2602.17914's learned filtered-ANN planner already swaps strategy per query from live statistics, and pluggable, GUC-tunable query planners are ordinary RDBMS practice (Postgres planner cost parameters, SQL Server plan hints) — what is specific to Datum is applying that ordinary shape to a slot most RAG frameworks never built at all, and treating "ship a rule table now, earn a smarter policy later without touching the interface" as an explicit, load-bearing engineering discipline rather than an incidental implementation detail.

### Resolving the five stance conflicts

The judge panel and the source proposals disagree with each other in five specific, load-bearing places. Naming the resolutions here, once, is this document's actual intellectual content; the mechanisms live in the sections cross-referenced below.

1. **Determinism (systems-db, evidence-first) vs. adaptivity (learned-policy).** A reproducible plan and a continuously-improving plan-selection policy look incompatible until replay is defined correctly. Datum's `Plan.replay()` reconstructs the recorded trace — the *realized* action, its propensity, and the exact policy version that produced it — not a re-execution against whatever policy is champion today. A stochastic policy at a pinned version can still have picked differently on the day; recording the action and propensity (not just the version) is what makes this exact, borrowing learned-policy's `StageTrace` shape directly. See §Core abstractions, `Plan`; §Subsystems, Query & planning.
2. **Minimalism (agent-native: "thin contract, get out of the way") vs. completeness (systems-db: a full compiled query language, CAL).** Datum keeps systems-db's internal plan IR but **demotes it to optional expert/internal plumbing** — the agent-facing surface is the small verb set in axiom 8, full stop. This is a deliberate, partial rejection of the winning skeleton's own proposal: CAL is never the *required* interface a model or a weak-model shim must learn. See §Anti-scope; §Core abstractions, Agent Tool Surface.
3. **Partition-based ACL (memory-os) vs. predicate-based ACL behind a conformance suite (systems-db, agent-native, learned-policy).** Neither wins outright: partitioning is combinatorially unsafe for realistic enterprise entitlement lattices (role × region × trial × tier); predicate filtering has a documented four-year history of failing open (LangChain4j #2513, Spring AI #3577) even with a conformance suite catching most of it. Datum's rule: **partition on the coarse, low-cardinality dimension** (tenant, department, environment) **and use a conformance-tested typed predicate for the fine-grained residue** (role, trial, IRB tier), with low-privilege recall measured continuously on both paths so whichever one is silently starving a caller gets caught rather than assumed away. See §Subsystems, Security & governance.
4. **Registry-bound authority hierarchy (evidence-first's central axiom) vs. general applicability.** All three judge lenses named the same fatal flaw: a curated authority tier (label > guideline > systematic review > RCT > …) generalizes from one medical-vertical ablation and has no coherent meaning for a Slack-and-wiki corpus, which is most enterprise deployments. Datum keeps `authority_tier` as an **optional, registry-bound field that defaults to `UNVERIFIED` everywhere no registry exists**, and makes the domain-general mechanism the load-bearing one: corroboration count (minimum independent origins), freshness, and `trust_class`, which degrade to a working signal even when every document in the corpus is `UNVERIFIED`. See §Subsystems, Evidence & trust.
5. **"No memory subsystem, full stop" (agent-native's anti-scope) vs. "the write path is the whole point" (memory-os's central thesis).** Both are partially right about different things. Agent-native is right that a memory *product* — extraction heuristics, what-to-consolidate judgment calls, forgetting policy UX — is not a retrieval framework's job. Memory-os is right that the write-path *primitives* underneath any such product (transactional writes, idempotency, bitemporal versioning, provenance-on-write) are exactly the kind of thing CI-06 and CI-07 already require Datum to build for documents, and building them twice — once informally for a memory product, once formally for the corpus — is the stranded-cost pattern the taxonomy warns about everywhere else. Datum pulls the primitives into the kernel (axiom 3) and keeps the product-level policy decisions (what to extract, when to consolidate, whether an agent gets write tools at all) pluggable and, by default, off. See §Subsystems, Memory & mutation.

**L0 — Object storage.** *Responsibility:* durable byte-level storage of raw source material (PDFs, exports, transcripts). *Interface:* none Datum-specific — any S3-compatible or filesystem blob store. *Builds on:* the "object storage as source of truth" pattern turbopuffer and Lance already validated at the index layer, generalized here to the whole corpus rather than just vectors.

**L1 — WAL.** *Responsibility:* the single writer path; every insert, patch, delete, and ACL change is a content-hashed, append-only transaction. *Interface:* internal — nothing above L2 writes except by appending here. *Builds on:* forty years of write-ahead-logging discipline (Postgres, any relational engine); this is the mechanism, per axiom 3, that makes CI-06's "mutating one document is O(changed content)" a property of the architecture, not a best practice.

**The L0/L2 seam, named and closed, not assumed.** `supersede`'s atomicity claim (§Core abstractions #2 — closing the old record's `tx_to` and opening the new record's `tx_from` in the *same* WAL append) is entirely a within-L2 (Postgres) transaction and holds on ordinary database grounds. What it does not, by itself, cover is the seam between L0 (object storage, holding raw blobs) and L1/L2 (Postgres, holding the WAL and metadata) — two different systems with no two-phase-commit protocol between them, which an MVP that splits blobs from metadata across two systems must not paper over. The invariant that actually closes this seam is simpler than distributed transactions and is standard content-addressed-store practice: **a blob is written to L0 and durable *before* any WAL entry in L2 is appended that references its content hash, never the reverse.** Because L0 blobs are content-addressed, a retried or duplicated blob write is idempotent by construction (same bytes, same hash, same object — writing it twice is a no-op); the only failure mode is a crash between the L0 write and the L2 append, which leaves an orphaned, unreferenced blob in L0 (harmless, garbage-collectable) and *never* a WAL entry pointing at content that was never durably written. This is the same sequencing Git uses for its own content-addressed objects (write the blob, then reference it from a tree/commit) and is sufficient for correctness without requiring distributed-transaction machinery: the WAL append is the single, sole commit point, and nothing above L2 ever observes a half-written record because nothing is ever referenced before it exists.

**L2 — Ground Store.** *Responsibility:* the canonical, bitemporal, typed record store — the only layer that is "mutable," and only by supersession, never by overwrite. *Interface:* `Record` (§Core abstractions #1). *Builds on:* Docling-class structural IR for the typed shape; bitemporal database theory (valid-time + transaction-time) for versioning, generalized here from Zep/Graphiti's conversational-edge-only scoping to the base record type itself, per axiom 3's grafted mechanism.

**L3 — Write Orchestrator.** *Responsibility:* admission control (schema and precondition checks, quarantine of low-confidence or contract-violating writes) and dispatch to a per-source-class `WritePolicy`. *Interface:* `WriteOp` (§Core abstractions #2). *Builds on:* memory-os's write-policy pluralism — one transactional algebra, source-specific policies plugged in — resolving stance conflict #5.

**L4 — Derivation Engine.** *Responsibility:* a DAG of registered `View` definitions (chunk → embed → enrich → graph-extract), each lineage-tagged and budgeted. *Interface:* `View` (§Core abstractions #3). *Builds on:* content-defined (rolling-hash) chunking from the rsync/CDC tradition — a chunk's identity is a function of its content, not its byte offset, so editing one paragraph invalidates only the touched chunk and its dependents; classical incremental-view-maintenance (IVM) literature, extended with a **refresh budget and staleness SLO** because an LLM-enrichment view costs dollars and seconds per unit, not microseconds.

**L5 — Physical Operator Layer.** *Responsibility:* grep/regex, BM25, ANN, late-interaction, graph traversal, and SQL-predicate operators, each a typed `plan/execute/cost_model` contract. *Interface:* `Operator` (§Core abstractions #4). *Builds on:* proven engines behind each operator (an existing Lucene/Tantivy-class BM25 engine, a DiskANN-lineage or IVF+RaBitQ ANN engine) — Datum does not re-derive index math; it costs and conformance-gates existing math.

**L6 — Plan Compiler.** *Responsibility:* compiles a logical intent (principal, policy, budget) into a physical plan against live statistics; plan-selection is itself a versioned `Policy` in a slot, not a hard-coded optimizer. *Interface:* `Plan` (§Core abstractions #5). *Builds on:* System R's logical/physical split as the founding idea; the learning-loop machinery is imported directly from off-policy-evaluation and always-valid sequential testing, decades-settled in search ranking and simply never re-imported into RAG.

**L7 — Evidence-State layer.** *Responsibility:* wraps physical output into a typed, provenance-carrying, conflict-aware, calibrated result. *Interface:* `EvidenceState` (§Core abstractions #6). *Builds on:* cheap uncertainty estimators (arXiv:2501.12835) for sufficiency without labels; Astute RAG-style conflict surfacing rather than silent fusion.

**L8 — Agent Tool Surface.** *Responsibility:* the only interface any consumer — frontier policy, weak-model shim, or human — ever calls. *Interface:* the five read verbs plus three capability-gated write verbs (§Core abstractions #7). *Builds on:* Anthropic's own tool-design guidance (consolidated, token-efficient, semantically-named) and the s3 pattern (decoupled, cheaply-retrainable default searcher) for the weak-model consumer.

**Cross-cutting: Eval / Promotion / Drift.** Taps L1 (writes), L3 (admission decisions), L4 (view changes), and L6 (plan outcomes) to run a self-bootstrapping regression loop and a debiased promotion pipeline as default artifacts, not a paid tier. Detailed in §Subsystems, Learning & adaptation.

**Cross-cutting: Governance.** The mandatory conformance suite (L5 registration gate), the entitlement suite (principal-scope enforcement), the frozen-kernel symbol-diff CI gate (checked against the previous minor version — a new exported kernel symbol requires deleting one), and a "governed" security profile that refuses to start without required controls declared. Detailed in §Subsystems, Security & governance.

### Worked example: a request through all nine layers

A support agent asks, on behalf of a logged-in principal with `region:EU, dept:finance` entitlements, "what's our refund policy for enterprise customers in the EU?"

1. The frontier policy (or `SearcherShim` on behalf of a weak model) calls `search(query, path_glob=None)` at L8. No principal, no call: `current_principal()` resolves from the session, never from anything the model supplies.
2. L8 compiles the call into a `Plan` at L6 — intent, principal, a default `Budget`. The plan-selection policy occupying the fusion-weight slot is today's champion: a declared rule table, not a learned model, unless Phase 2's promotion loop has already promoted a challenger for this tenant.
3. L6 resolves the coarse ACL dimension first: the principal's `dept:finance` namespace is selected at L2/L4 before any operator runs — there is no cross-namespace predicate for a backend to mistranslate. Within that namespace, the fine-grained residue (`region:EU`) is evaluated by a conformance-tested `Operator`, fail-closed: a predicate-evaluation error excludes the row, never includes it.
4. L5's registered operators fire — BM25 and one dense operator, fused per the champion policy's declared weights — reading L4's `lexical` and `dense_v2` Views, both built from the same L2 snapshot, so their candidate sets share a coordinate space rather than being fused as a coin flip.
5. L7 wraps the candidates into an `EvidenceState`: `sufficiency=0.81`, `status="ok"`, `authority_tier` mostly `UNVERIFIED` (this corpus has no curated registry), `trust_class="trusted"` (every source here is an ingested document, not an agent-inferred write).
6. L8 returns grep-shaped `SearchHit`s to the model; `authority_tier`/`trust_class`/`verdict` never reach the model's context — held server-side, keyed by `hit_id`, available to a downstream disambiguation or citation step.
7. The full call is persisted as one typed trace at L6, EXPLAIN-able immediately (`plan.explain()`) and REPLAY-by-record forever after — whether this was the only retrieval call in a single-shot pipeline or the fortieth call in a long agentic loop, the trace shape is identical.
8. Three months later, the fusion-weight slot has crossed its declared feedback floor for this tenant; a challenger cleared its promotion gate last week and is now champion. Replaying today's `plan_id` from step 2 reconstructs *that day's* champion and its logged propensity by default — a separate, explicitly-named call is required to see how the same intent resolves under today's champion instead.
9. A departing employee's personal working-memory scope (annotations on this policy, written via the opt-in agent-write path) is forgotten: *(Phase 1 and later — §MVP definition; a v1 deployment runs this step as `forget(mode="tombstone")` instead, which does not clear the bar below)* `forget(mode="crypto_shred")` shreds that scope's key, `LineageManifest.propagate_forget()` walks every derived View the scope touched, and returns a completion proof. The underlying refund-policy documents — a different `policy_id`, ingested by `DocumentPolicy`, not the departing employee's personal scope — are untouched, because provenance separates "who annotated this" from "what the policy says."

### 1. `Record` — the canonical, bitemporal, typed substrate entity

Merges systems-db's content-addressed `Corpus`/typed IR with memory-os's bitemporal `Record` and `ProvenanceCapsule`.

### 2. `WriteOp` — the transactional write path, source-specific policies

```python
class WriteOp(Protocol):
    def assert_(body, valid_from, provenance, policy_id, idempotency_key=None) -> RecordID: ...
    def supersede(old_id, body, valid_from, provenance, idempotency_key=None) -> RecordID: ...
    def invalidate(id, valid_to, reason) -> None: ...
    def consolidate(source_ids, summary_body, policy) -> "ConsolidationView": ...
    def forget(id, mode: Literal["tombstone", "crypto_shred"]) -> "ErasureReceipt": ...

class WritePolicy(Protocol):
    name: str; version: str
    def ingest(self, raw: RawInput, principal: Principal) -> list[WriteOp]: ...
```

`assert_` with a repeated `idempotency_key` is a no-op returning the original id — this is what defangs Mem0 `#5245`-class silent-drop-or-duplicate under retry. `supersede` closes the old record's `tx_to` and opens the new record's `tx_from` in the *same* WAL append, so no concurrent reader ever sees both or neither — the `#4892` concurrent-corruption fix.

**A race the idempotency key alone does not cover, fixed at the kernel, not the caller.** `idempotency_key` protects a *retry* of an identical write. It does nothing for two concurrent ingestion pipelines racing on the *same new* span for the first time: `DocumentPolicy.ingest` (below) reads `find_span()` then conditionally writes, and two workers can both observe `prior=None` and both call `assert_`. The kernel closes this the way a database closes it — not by asking every `WritePolicy` author to get the read-then-write right, but with a uniqueness invariant enforced underneath `assert_` itself: at most one currently-live (`tx_to IS NULL`) record per `(source_id, stable_key)`. A losing concurrent `assert_` does not silently succeed or silently drop; it fails the uniqueness check and the kernel converts it to a `supersede` against whichever record won, transparently to the caller. This is the same compare-and-swap discipline a unique index gives a naive application-level "check then insert" — moved into the kernel so no `WritePolicy`, including ones third parties register, can reintroduce the race by omission.

**A second invariant the kernel enforces regardless of which `WritePolicy` emitted the write.** Nothing above stops a `WritePolicy` from *claiming* `authority_tier="primary"` for content nobody verified — the exact "type systems check sockets, not semantic contracts" root cause CI-02 diagnoses, one level up, inside the mechanism meant to fix CI-04. The kernel clamps it:

```python
# Enforced on every WriteOp before it reaches the WAL — not a WritePolicy-author
# convention, and not something a registered policy can opt out of.
def _kernel_admit(op: WriteOp, principal: Principal) -> WriteOp:
    if op.provenance.authority_tier in {"primary", "corroborated"} \
       and "verified_source" not in principal.capabilities:
        op.provenance.authority_tier = "inferred"   # clamped, never trusted on say-so
    return op
```

`verified_source` is an administrator-granted capability on a `Principal`, never something a model, a `WritePolicy`, or an agent's own inferred write can self-assert — the same discipline `trust_class="untrusted"`-by-default already applies to one field, now applied to the field an unverified writer would otherwise be able to inflate unchecked.

**Day 1** — a document re-ingest supersedes only the changed span, because content-defined chunk identity means an unchanged span produces the identical content hash:

```python
class DocumentPolicy(WritePolicy):
    name, version = "document-v1", "1.0"
    def ingest(self, raw, principal):
        ops = []
        for span in self.parser.parse(raw).spans:
            record = self._to_record(span, principal)
            prior = self.store.find_span(raw.source_id, span.stable_key)
            if prior is None:
                ops.append(WriteOp.assert_(record.body, raw.observed_at, record.provenance,
                                            raw.policy_id, idempotency_key=record.id))
            elif prior.id != record.id:                        # content actually changed
                ops.append(WriteOp.supersede(prior.id, record.body, raw.observed_at, record.provenance))
            # else: unchanged span, no op — nothing re-embeds
        return ops
```

**Expert** — a conversational-memory policy that never supersedes at extraction time (a later utterance doesn't replace an earlier one; it gets consolidated alongside it, through a separate, auditable operation) — the concrete difference between "one write model" (rejected, per stance-conflict #5) and "one write path, pluggable policies" (adopted):

```python
class ConversationPolicy(WritePolicy):
    name, version = "conversation-extract-v1", "1.0"
    def ingest(self, raw, principal):
        return [WriteOp.assert_(c.text,
                    provenance=ProvenanceCapsule(writer=principal, ingestion_path=self.name,
                        authority_tier="inferred", trust_class="untrusted",   # untrusted BY DEFAULT
                        source_version=self.extractor.version),
                    policy_id=raw.policy_id, idempotency_key=c.dedup_key)
                for c in self.extractor.extract(raw.transcript)]

orchestrator.register_policy(source_type="pdf_upload", policy=DocumentPolicy(parser=my_parser))
orchestrator.register_policy(source_type="chat_session", policy=ConversationPolicy(extractor=fact_extractor))
```

`trust_class="untrusted"` on every agent-inferred write is the specific mechanism that closes the CI-04 self-poisoning loop: an agent's own inferred write does not inherit the trust of the sources it read, so a hallucinated preference cannot re-extract itself into permanent "fact" the way Mem0's forensic audit found happening 808 times.

**`PromptArtifact`: closing a gap this revision found inside Datum's own kernel, not just in the frameworks it critiques.** CI-11 names "hidden prompts" — an unregistered, unversioned, non-diffable template — as a core defect of the black-box pipelines Datum exists to replace. On inspection, Datum's own internal LLM-mediated steps (`contextualize()`'s enrichment generation above, the `autorater-v1` sufficiency judge, golden-set judge grading in §Subsystems, Evaluation & observability) were specified as plain function calls to an opaque `llm_generate_context`/judge prompt — the identical defect, one layer down. The fix: every internal LLM-mediated step Datum itself runs is registered as a `PromptArtifact` — a named, versioned prompt template stored in the same derivation-manifest lineage as an embedder or parser version, diffable in CI the way a code change is. A change to `contextualize-prompt-v3`'s wording is a version bump that shows up in `LineageManifest`, the same as swapping the embedder — not a silent edit to a string constant nobody tracks. This does not extend to *generation-time* prompts (the calling agent's own system prompt, a downstream RAG pipeline's answer-synthesis template) — those remain out of scope because Datum owns no generation loop (§Anti-scope) — but it closes the part of the gap that was inside Datum's own reach and, on the original draft, wasn't closed.

### 4. `Operator` — the conformance-gated physical operator contract


**On the comparison this draws with LangChain, stated precisely.** LangChain's own `langchain-tests`/`VectorStoreIntegrationTests` package (842 lines, independently fetched and read in full for this project's `common-issues.md` CI-03 verification) exists and vector-store integrations do subclass and pass it — so "LangChain has zero conformance tests" is false if read as a blanket claim, and this document does not make that claim: every place below scopes it to *filter-algebra and score conformance* specifically, because on that specific axis the suite contains zero test methods — only CRUD, idempotency, and get-by-ids. The differentiation Datum claims is narrower and, on direct inspection of the source, still holds: a conformance gate covering filter algebra, score contracts, and tenancy fail-closed cases, enforced as a hard registration refusal rather than an optional integration-test target a mistranslating backend can ship without ever running.

**A test class this revision adds, closing a gap the coverage audit found: fail-closed on stale entitlement data, not just on filter algebra.** The conformance suite as originally specified verifies that a predicate operator translates a filter *correctly* — it says nothing about whether the entitlement data (role/trial/tier membership) the predicate evaluates against is *current*. Identity/ACL-sync remains explicit anti-scope (§Anti-scope) — Datum does not mirror an identity provider — but a stale entitlement snapshot silently reproduces exactly the tenant-isolation failure this mechanism exists to prevent, and it would pass every filter-algebra test while doing so. The fix is not to solve entitlement freshness (out of reach for a retrieval framework) but to make staleness a typed, checkable, fail-closed condition rather than a silent one: every entitlement snapshot a predicate operator evaluates against carries an `as_of` timestamp and a policy-declared `max_staleness`; the conformance suite's tenancy class now includes a mandatory case asserting that a snapshot older than `max_staleness` causes the predicate to **exclude**, never include, the row it would otherwise have to guess about. This converts a silent collapse into a loud, typed degradation — the same fail-closed-vs-degrade-gracefully split axiom 4 already draws between a security filter and a relevance filter — without pretending Datum now owns identity freshness, which it does not.

### 5. `Plan` — compiled query, plan-selection-as-policy-slot, EXPLAIN, replay-by-record

```python
plan = Plan.compile("""
  EVIDENCE FROM contracts
  WHERE intent = "EMEA churn drivers, Q3 2026"
  NEED sufficient
  AS principal = user("alex@acme.com") POLICY "default-acl"
  BUDGET tokens <= 4000, latency <= 800ms, dollars <= 0.02
""")   # the CAL surface above is OPTIONAL EXPERT PLUMBING (stance-conflict #2) — most
       # callers never write this; search()/fetch() below compile to it invisibly.

print(plan.explain())
# Plan(cost_estimate={tokens: 3200, latency_ms: 410, dollars: 0.008}, plan_selector="fusion-v3")
#  -> BM25(k=50) + ANN(k=50, index=embeddings_v3) -- RRF[weights=fusion-v3]
#  -> rerank(cross_encoder, top=20)
#  -> acl_filter(namespace="tenant:acme", predicate="role in {finance-eu}", pre_rank=True)  [fail-closed]
#  -> sufficiency_check(method="autorater-v1")

result = plan.execute()
if result.status == "insufficient_evidence": escalate_or_abstain(result)

# Expert: replay-BY-RECORD — re-render the persisted trace (query, realized fusion-v3
# weights, its logged propensity, the exact candidates it considered), not a
# recomputation against today's corpus or today's champion policy.
old = Plan.replay(plan_id="pl_9f2a...")                      # exact past behavior, reproduced
today_rerun = Plan.replay(plan_id="pl_9f2a...", against="current_champion")   # explicit opt-in
                                                                                 # re-execution, a
                                                                                 # different, named call
diff = old.diff(today_rerun)   # drift report — separates "what happened" from "what would
                                # happen now," instead of silently conflating the two
```

`fusion-v3` above is not a hard-coded constant: it is a versioned `Policy` occupying the fusion-weight slot in the Plan Compiler, exactly the "optimizer demoted to a policy" resolution from §Design axioms. v1 ships the slot filled with a declared, dated rule table; §Subsystems, Learning & adaptation, describes how a challenger earns promotion into it.

**On replay-by-record's own provenance, stated plainly.** The mechanism — persist the realized action, its logged propensity, and the exact policy version, then replay the record rather than recompute against a live policy — is not new to this document. It is the "Replay Method" from contextual-bandit off-policy evaluation (Li, Chu, Langford & Wang, WSDM 2011), which logs exactly this triple and replays matched history rather than recomputing under a new policy, and it is the same idea Temporal.io productizes at the systems level: an Event History replayed against workflow code to reproduce exact past behavior, with a separate, explicitly-named mechanism required to run new code against old history — precisely the `against="current_champion"` split above. Datum's contribution is narrowly the transposition of an established idea to a retrieval Plan IR, not the reconciliation idea itself. **A consequence of that transposition worth stating honestly: at v1, the propensity is trivially 1.0.** The MVP plan-selector is a deterministic rule table (§MVP definition), so there is no distribution over actions to log a probability against — `Plan.replay()` still reconstructs the exact realized plan and is still the correct mechanism for CI-11/CI-25's reproducibility acceptance test, but the *debiasing* value of a logged propensity (the reason the WSDM 2011 method records one at all) only becomes load-bearing once Phase 2 installs a stochastic or learned policy behind the slot. Shipping the full trace shape now and having it degrade gracefully to a deterministic special case, rather than building a second, simpler trace format for v1 and migrating later, is the actual engineering bet.

### 6. `EvidenceState` — typed, calibrated, conflict-aware, abstention-capable

The typed-outcome move itself — `insufficient_evidence`/`conflicted` as a plan's type signature rather than a generation-time surprise — is credited above to Astute RAG and a cheap-uncertainty-estimator paper, and was never presented as independently invented; it is the same operative design already shipping in contemporary RAG-verification research (LIT-RAGBench's `{SUPPORTED, REFUTED, INSUFFICIENT}` status mapping directly to an `{ANSWER, ABSTAIN}` decision; SURE-RAG's identical typed-sufficiency-gates-abstention architecture), named here explicitly rather than left as an unattributed "multiple 2026 papers."

**A signature inconsistency the coverage audit caught, and what it does and doesn't mean.** `search()` shows no `principal` parameter while `navigate`/`fetch` do — this reads, uncorrected, as if `search()` compiles without one, directly contradicting axiom 4's "does not compile without a value." It doesn't: `search()`'s body calls `corpus.retrieve(query, principal=current_principal(), ...)`, so a principal is still a mandatory argument to the actual plan-compilation call underneath — the difference is only where in the call chain it's threaded through explicitly. That said, the stylistic difference was real and `current_principal()`'s own resolution mechanism was previously left unspecified at exactly the seam a hostile reviewer should press hardest on, so it is specified here rather than left implicit: `current_principal()` reads a request-scoped context populated exactly once, at MCP session/connection time, by the deployment's own auth middleware (the bearer token, mTLS identity, or session cookie the transport layer already validated) — never from a tool-call argument, and never from anything a model supplies. This is deliberate, not an oversight: the model-facing JSON tool schema (above) omits `principal` for **every** read verb, `search()` included, because accepting a model-supplied principal at all would be a prompt-injectable escalation path — a planted document could otherwise instruct the model to call a tool with an elevated principal. `navigate`/`fetch` showing `principal` as an explicit Python parameter documents the same server-resolved value threaded through the dispatcher explicitly, not a different trust model; `current_principal()` failing to resolve (no session context populated) raises, rather than defaulting to `None` or an anonymous/admin principal, so an unauthenticated call fails closed at exactly this seam rather than silently proceeding.

**Dual consumer.** A frontier trained policy calls these eight verbs directly — no scaffolding tax. A weak or local model is handed `SearcherShim`, a small, cheaply-trained-or-prompted default policy (the s3 pattern: 2.4k training samples, frozen generator, model-agnostic) that formulates queries, chooses `navigate` vs. `fetch` vs. `search`, and decides when sufficiency is met — the same eight verbs, mediated rather than duplicated:

```python
from datum.policy import SearcherShim
shim = SearcherShim(generator=my_local_llm, corpus=corpus, principal=principal)
answer = shim.run("What drove EMEA churn in Q3?")
```

## Subsystem specifications

### Ingestion & derivation

**Design.** Ingestion is a `WritePolicy.ingest()` call that parses raw input into typed `Record`s and emits `WriteOp`s (§Core abstractions #1–2); derivation is a DAG of `View` definitions reading only from the canonical Ground Store, never from another View (§Core abstractions #3). Chunk boundaries are content-defined — specifically FastCDC (Xia et al., USENIX ATC 2016), a rolling-hash function that picks a split point wherever a fixed-length window of bytes hashes below a threshold, the algorithm rsync-class sync and content-defined backup deduplication have used for over a decade — so a chunk's identity is a function of its content, not its byte offset, and survives unrelated edits elsewhere in the document. This is the concrete mechanism behind CI-06's "only the touched chunk and its dependents re-derive" acceptance test, not a best-effort optimization that happens to usually work. Naming the source plainly: FastCDC itself is old, well-known dedup/backup engineering, not a Datum invention; as far as this project's search turned up, no shipped RAG framework applies it to chunk-identity specifically — a mechanical transplant of a 2016 technique into an adjacent domain, not a research contribution, and §Research contributions grades it that way.

**Reconciling content-defined boundaries with the structural IR — a real tension this design did not originally resolve, fixed here rather than left as a named gap.** Plain rolling-hash CDC cuts wherever the hash condition fires, which is a semantically arbitrary byte position; L2's structural IR simultaneously demands that a table's cells and a section's heading stay intact within one chunk. Unconstrained, these pull against each other: CDC's shift-invariance (an edit touches only the chunks near it) is exactly what breaks if boundaries are instead snapped to structural units, and structural coherence is exactly what breaks if boundaries are left to fire at arbitrary byte offsets inside a table row. The fix is boundary-constrained CDC: the candidate split points are the *union* of {rolling-hash trigger positions, structural-unit boundaries from the parser's IR (table start/end, section start/end, page break)}, and the actual boundary used is the nearest structural boundary at or before each rolling-hash trigger — never inside a table or across a header/body split. This degrades CDC's granularity from paragraph-level to section-or-table-level around structural content (an edit inside a large table can invalidate that whole table's chunk, not just the touched cell), which is a real, stated cost, not a free lunch — but it preserves both properties where they matter most: prose reflows at fine CDC granularity as designed, and no chunk ever splits a table row or separates a heading from the content it governs.

**Defaults.** One structural parser (Docling-class IR) behind the canonical interface; a dated default view profile (`"2026-hybrid-rerank"`) providing hybrid lexical+dense retrieval with reranking out of the box (closing CI-14's frozen-top-k-2 pattern at ship time, before the learning loop ever runs); per-span parser confidence carried through, with low-confidence spans queryable rather than silently trusted or silently dropped.

**Failure handling.** A destructive cross-stage composition (a cleaner stripping the delimiter its own chunker requires) is rejected at write time by a registered precondition, not discovered as one giant chunk in production. A parser failure quarantines the affected span (`trust_class="quarantined"`) rather than either blocking the whole document or silently admitting low-confidence content. Datum does not claim to beat OHR-Bench's ~14% F1 parsing-fidelity ceiling — that is a modeling problem, not an architecture problem, and is named as such rather than glossed over.

### Index & storage

**Design.** The Ground Store (L2) is the only canonical artifact; every index — lexical, dense, multi-vector, graph, or a closed vendor backend — is a disposable, rebuildable `View`. Physical operators (L5) wrap proven, existing engines (BM25 via an existing Lucene/Tantivy-class engine; ANN via a DiskANN-lineage or IVF+RaBitQ engine) behind a conformance-gated contract; Datum does not re-derive index math.

**Defaults.** Two operators at MVP (grep, BM25) plus one ANN operator; graph and late-interaction operators are registered later, off by default, each declaring cost/coverage/freshness in the same manifest schema so a plan can route around a channel that is stale or narrow rather than trusting it uniformly.

**Failure handling.** A `dual_read` cutover serves the old View while a new one (a re-embed, a migrated backend) builds, with a retrieval-overlap drift report gating promotion before the old View retires — never a silent full re-embed on a vendor's billing meter, never an unversioned in-place swap that invalidates yesterday's citations. `LineageManifest.rebuild(view_kind, backend)` is the literal "kill-the-vendor drill": with Datum's own binaries deleted, a third party rebuilds a recall-equivalent system from the exported Ground Store and View manifests alone.

### Query & planning

**Design.** `search()`/`fetch()`/`navigate()` compile to a `Plan` (§Core abstractions #5): a logical intent plus principal, policy, and budget, resolved against live operator statistics into a physical plan. Plan-selection — which operators fire, at what fusion weights, at what rerank depth, when to stop — is itself a versioned `Policy` occupying a slot in the compiler, not a built cost-based optimizer and not a frozen heuristic.

**Defaults.** The slot ships filled with a declared, dated rule table (fusion weights and rerank depth benchmarked against BEIR/MIRACL-class baselines, stop/abstain on an NQC-style score-variance threshold) — zero learned components at v1, by design (§MVP definition). Every plan emits an `EXPLAIN` artifact before execution and a persisted, replayable trace after, by default, on every call — not an opt-in observability SKU. "Against live statistics" in L6's own responsibility line (§The architecture) describes the mature, Phase-2-and-beyond system; the v1 rule table itself consumes only declared, static configuration (corpus size band, presence of a dense index) and does not require a live selectivity/cost-telemetry loop to run — calibrating *that* loop well enough to drive real routing decisions is one of this design's genuinely hard, unsolved parts (§Limitations & honest tradeoffs), not something MVP depends on.

**Hot-path budget — three components a single `search()` call touches that this document did not originally cost, made explicit here.** Walking one call end to end surfaces three server-side components riding the read path, none of them free, none of them previously named in a cost model despite `Budget`/`CostTrace` being a headline mechanism:

| Component | What it does | Per-call cost (illustrative, at 100 QPS × ~50 candidates/query) | Design response |
|---|---|---|---|
| `HitRegistry` write (out-of-band envelope) | Persists `hit_id → {record_id, authority_tier, trust_class, verdict, plan_id}` so a later `fetch(hit_id)` or disambiguation step can resolve it | ~5,000 small (<1KB) upserts/sec | TTL'd (default 1h — bounded to session length), replicated key-value tier (the same durable, cross-replica cache class already needed for session state) — *not* server-local memory, so a second replica serving `fetch()` sees it. A stateless fallback (an HMAC-signed token encoding `record_id`+snapshot version, decodable without shared state) is named explicitly for single-replica or edge deployments that cannot run a shared cache — it trades revocability (a token for a since-forgotten record stays decodable until snapshot rotation) for zero shared-state cost, and a deployment must pick one, not discover the gap in production. |
| Plan trace persistence (EXPLAIN/replay-by-record) | Writes query + realized plan + candidate set + policy version per call | one write/call, same order as query volume | Default is asynchronous/buffered, not synchronous on the caller's critical path — a stated, bounded loss window (traces from the last flush interval, typically low single-digit seconds) is the named cost of a crash, not silently assumed away. Trace-store write throughput, not BM25/ANN read latency, is realistically the first bottleneck at scale, and is named as such rather than discovered later. |
| Fine-grained ACL predicate evaluation | Evaluates the conformance-tested predicate against the entitlement snapshot | one evaluation per candidate row in the fine-grained residue | Bounded by the same `Budget` that bounds everything else in the plan; the entitlement-staleness fail-closed test (§Core abstractions #4) adds a freshness check to this evaluation, not a new unbounded cost. |

**Failure handling.** Budget exhaustion degrades tier-wise (full hybrid → sampled → embedding-only), flagged `truncated`, never silently overspent. A plan that cannot clear its sufficiency threshold returns `insufficient_evidence` rather than a confident answer over thin evidence. Replay of a plan whose selected policy has since been rolled back reconstructs the *original* recorded behavior by default; reconstructing behavior under today's champion is a separate, explicitly-named call (`against="current_champion"`), so the two are never silently conflated.

### Evidence & trust

**Design.** `EvidenceState` (§Core abstractions #6) carries provenance, an optional registry-bound `authority_tier` defaulting to `UNVERIFIED`, a `trust_class`, and a corroboration count, kept structurally out-of-band from the tokens a consuming model attends to (§Core abstractions #7). Conflicts between sources are a first-class, structured field — never silently fused into one averaged answer.

**Defaults.** `authority_tier` starts `UNVERIFIED` for every record until a deployment populates a curated registry (a real guideline repository, a verified-publisher list); the domain-general fallback — corroboration count, freshness, `trust_class` — is what most deployments run on permanently, and is designed to degrade gracefully rather than collapse when no registry exists (resolving stance-conflict #4). `min_independent_origins` defaults to 1 (no corroboration requirement) and is raised per-policy for higher-stakes queries; a policy that raises it is a per-query escalation, not a global strict/fast mode switch, following evidence-first's rigor-dial argument that the sufficiency signal computed on the cheap first pass — not a deployment-wide setting — should decide whether a second, more expensive corroboration pass runs at all.

**Failure handling.** Salience-induction and other content-innocent attacks (83.3% attack success in the literature while every individual claim stays true) are **not** solved here — no content-inspection defense reaches this class, and Datum does not claim otherwise, in this section or anywhere else in this document (§Research contributions #5 and §Issue-coverage traceability CI-04 are both worded to match this sentence, not to claim more than it does). Structurally preventing retrieved text from reaching the instruction position (CaMeL-class provable isolation, ~7 utility points) is treated as an integration point Datum's typed values are designed to compose with, not a mechanism this design invents.

**The out-of-band mechanism's own provenance and its unspecified consumer, both stated plainly.** The mechanism itself — keeping authority/trust/provenance server-side and resolving it only through an opaque `hit_id`, never re-serializing it into the model's own context — already ships: LlamaIndex's Index v2 legal-kb (July 2026) exposes grep-shaped `retrieve`/`findFiles`/`readFile`/`grepFile` tools returning opaque citation ids (`cite:c7f2qa`-shaped) resolved to source only in a UI layer, and arXiv:2605.29082 ("The Importance of Out-of-Band Metadata for Safe Autonomous Agents: The Redpanda Agentic Data Plane") independently generalizes exactly this pattern — an agent-inaccessible, infrastructure-level channel carrying policy/identity/audit signal alongside but outside the model's data path — as a named, general agent-safety mechanism, not something RAG or Datum originates. What raises attacker cost here is real, but it collects enforcement-grade metadata (`trust_class`, `authority_tier`, `verdict`) and hands it to a consumer this design does not build: every component that would *act* on it — guardrails, a hallucination detector, a disambiguation UI — is explicitly anti-scoped (§Anti-scope), so "closing" language anywhere in this document about this mechanism is an overclaim and has been corrected to "raising the cost of," not "closing," throughout this revision.

### Memory & mutation

**Design.** One transactional write path (`WriteOp`, §Core abstractions #2), source-specific `WritePolicy` dispatch, bitemporal versioning at the base `Record` type. This is the resolution of stance-conflict #5: the *primitives* (idempotent writes, atomic supersession, provenance-on-write) are kernel; the *policy* (what an agent extracts from a conversation, when it consolidates, whether it gets write tools at all) is pluggable and, by default, absent — Datum ships no memory *product*.

**Defaults.** Agent write verbs (`remember`/`supersede`/`forget`) do not appear in the tool list unless a deployment registers a `WritePolicy` for agent writes; when registered, every such write defaults `trust_class="untrusted"` and `authority_tier="inferred"`, regardless of how confidently the model states it. Consolidation (`WriteOp.consolidate`) produces a `ConsolidationView` — a reversible summary with a zero-cost-until-followed pointer back to the ground records it summarizes, never a replacement for them.

**Failure handling.** A repeated `idempotency_key` under retry is a no-op, not a duplicate or a silent drop (`Mem0 #5245`'s class of bug). Two concurrent writers to the same record either both succeed idempotently or one supersedes cleanly in one WAL append — never a corrupted index (`Mem0 #4892`'s class of bug). The kernel-enforced uniqueness invariant and the `authority_tier` clamp specified in §Core abstractions #2 apply here without exception: a `WritePolicy` racing on a first write to the same span is resolved by the kernel's compare-and-swap, not by trusting the policy's own read-then-write logic, and no `WritePolicy` — built-in or third-party — can self-assert `primary`/`corroborated` authority for content its writing principal isn't independently entitled to vouch for. `forget(mode="crypto_shred")` moves the unrecoverability guarantee to the key layer and returns a completion proof enumerating every derived View the erasure reached; `forget(mode="tombstone")` is retained for reversible staging use and is explicitly documented as **not** meeting the erasure bar. **`crypto_shred` itself is Phase 1, not MVP** (§MVP definition) — v1 ships `tombstone` only, so no deployment depends on the KMS this mode requires before that dependency has been hardened.

### Learning & adaptation

**Design.** Every tunable inside the Plan Compiler and Derivation Engine — fusion weights, rerank cascade depth, stop/abstain threshold, representation routing (dense/sparse/multi-vector), enrichment-view admission — is a named, versioned decision point with a declared default and a declared feedback-floor tier, following learned-policy's tiering discipline generalized onto systems-db's own slots:

| Decision point | Default (ships day 1) | Feedback floor for a challenger | Reward source |
|---|---|---|---|
| Stop / abstain | NQC-style score-variance threshold | ~10²–10³ | debiased accept/regenerate |
| Rerank cascade depth | fixed hybrid → cross-encoder cascade | ~10³ | debiased citation-click / task-success |
| Fusion weights | benchmarked static profile (`"2026-hybrid-rerank"`) | ~10³–10⁴ | contextual bandit on debiased reward |
| Representation routing (dense/sparse/multi-vector) | corpus-statistics-driven static rule, LIMIT-aware | ~10⁴ | golden-set win-rate, rarely production-fed |
| Enrichment-view admission | budgeted, sampled-QA gate | corpus-level, not per-query | golden-set ablation vs. a cheaper baseline |

A tenant whose traffic never crosses a floor is not broken — it is in Tier-A-only mode, and the operator console reports this plainly rather than silently, following learned-policy's own visible-feedback-floor discipline. A challenger for any slot is promoted only after clearing a **debiased** statistical bar: an inverse-propensity-weighted, doubly-robust (AIPW) off-policy value estimate against an **always-valid sequential test** (so a team checking the dashboard whenever they like never inflates a false-promotion rate), with guardrail metrics (cost, p99 latency, worst-slice quality) monitored through a canary before full rollout.

**Defaults.** Every decision point ships on its cheap Tier-A default, continuously re-validated against a zero-label, corpus-derived golden set (Chroma-style generative benchmarking) — a tenant that never crosses a feedback floor is not broken, it is "in Tier-A-only mode," and the operator console says so explicitly rather than silently. Stop/abstain and rerank depth are the first candidates for a learned challenger (post-retrieval control), following the one production study in the corpus that measured which side of the pipeline learning actually paid off on; pre-retrieval routing decisions default to cheap, corpus-statistics-driven rules and are re-evaluated primarily at ingest time against the golden set, not against noisy per-query production feedback.

**Failure handling.** A `DriftMonitor` watches query-distribution drift, corpus drift, and feedback-channel anomalies (the specific new attack surface a learning system creates: an adversary — or a hallucinating downstream agent — writing content whose later retrieval generates the feedback that reinforces retrieving it again) and **freezes** the affected slot back to its default unilaterally, before a human is paged, not after. Exploration for off-policy learning is strictly bounded within the post-authorization candidate set for a given principal; a policy that widens candidates "for exploration" is treated as a CI-05-class vulnerability and is caught by the same conformance suite that checks filter algebra. Correctly implementing this — debiased off-policy evaluation without also opening the feedback-poisoning surface just named — is decades-settled discipline in classical search ranking but genuinely new to import into a retrieval substrate whose write path is this permissive; it is named in §Limitations & honest tradeoffs as a hard part this design specifies a monitor for, not one it has proven closed.

### Evaluation & observability

**Design.** Every `Plan` execution emits an `EXPLAIN` artifact before and a persisted, replayable trace after, by default (§Core abstractions #5). At MVP, the regression signal comes from a small, fixed, human-curated set of query/expected-evidence pairs (§MVP definition) — not the generative bootstrap described next — gating any manual config change before it ships. **Phase 1 and later**, this is replaced by a zero-label golden set bootstrapped from the canonical corpus itself (Chroma-style generative benchmarking) and used to gate any `View` or policy-slot change before it reaches production traffic; generating a good synthetic golden set from an arbitrary corpus is itself a research-adjacent problem, not the cheap measurement-first win the original framing implied, which is why it is scheduled after a cruder but immediately trustworthy fixed set, not instead of one. Production telemetry (escalation events, abstention events, click/accept/regenerate signals) feeds back into both the golden set (re-weighting it toward the query distribution actually seen, closing CI-16's dashboard-terminated loop) and the promotion pipeline (as debiased reward signal for Learning & adaptation).

**Defaults.** Judges used for golden-set filtering and promotion gating are calibrated against a small human-anchored slice using PPI-style confidence intervals before any score can gate a promotion — a direct pre-emption of CI-15's self-collision risk (an uncalibrated judge grading its own homework is exactly the failure this subsystem exists to prevent, not reproduce). Where a deployment's model roster allows it, the judge is drawn from a different model family than the generator it grades, as a stated default preference, not a guarantee — cross-family judging reduces, but on its own evidence base does not eliminate, the shared-blind-spot risk named below.

**Failure handling.** A regression on any guardrail metric during canary reverts to the champion policy automatically; a human is notified either way but does not gate the rollback. Judge/teacher circularity (the same model family judging and generating) is bounded by calibration, not eliminated, and this is stated rather than hidden. Whether the self-bootstrapped golden set avoids becoming its own instance of this exact problem — an uncalibrated judge grading a set drawn from the same corpus it is judging — is named as an open question this document does not claim to have resolved (§Open questions).

### Security & governance

**Design.** Authorization defaults to **namespace partitioning on the coarse, low-cardinality dimension** (tenant, department, environment) — a principal's retrievable universe is a set of physical namespaces, so there is no cross-namespace ACL predicate for a backend to mistranslate. For the fine-grained residue (role, trial phase, IRB tier — the combinatorial part), Datum falls back to a **typed, conformance-tested predicate**, differentiated at the type level from a relevance filter (fail-closed vs. degrade-gracefully) so the two can never again share a code path the way CI-03 documents. **Low-privilege recall is a continuously measured, published metric on both paths** — the check that catches whichever mechanism is silently starving a caller, resolving stance-conflict #3 without asserting either mechanism alone is safe.

**Defaults.** Every registered physical operator must pass the mandatory conformance suite (filter algebra, score contract, tenancy fail-closed cases including the NOT-IN case that broke LangChain4j, and the entitlement-staleness fail-closed case added in §Core abstractions #4) before it can register at all — a hard refusal, not an aspirational test file.

**The kernel symbol budget, stated as a number, not a pledge.** A CI gate that diffs the public symbol surface against the previous minor version is the same pattern `cargo-semver-checks`/`cargo-public-api` (Rust), `japicmp` (Java), and `ApiCompat` (.NET) already enforce as off-the-shelf tooling — Datum's application of it to an agent-facing verb/type surface is not itself a new gate design, and is credited as such. What was missing from the original specification, and is the actual governance mechanism, is a stated number: an unbudgeted "a new symbol requires deleting one" rule is unfalsifiable, and — as the coverage audit that produced this revision found — was already on a collision course with this document's own Phase 1 roadmap (the fine-grained predicate ACL path needs new types under a kernel with no stated headroom). The kernel's public symbol table, counted directly against this document's own specification, stands at 35 exported types — not 31, and the discrepancy is worth explaining rather than quietly correcting: an earlier pass through this same revision counted 31 (`Record`, `ProvenanceCapsule`, `RecordID`, `PolicyID`, `Principal`, `WriteOp`, `WritePolicy`, `ErasureReceipt`, `ConsolidationView`, `View`, `LineageManifest`, `Operator`, `OperatorPlan`, `CandidateSet`, `CostEstimate`, `ConformanceSuite`, `Plan`, `Policy`, `Budget`, `CostTrace`, `EvidenceState`, `EvidenceItem`, `Conflict`, `CalibratedScore`, `SearchHit`, `StructureView`, `Evidence`, `ChangeSet`, `GovernedProfile`, `DriftMonitor`, `Corpus`) and then this very revision *added* four more while fixing other gaps — `PromptArtifact` (§Core abstractions #3, closing CI-11's hidden-prompts gap), and `Span`, `BoundingBox`, and `HitRegistry` (§Core abstractions #6 and §Subsystems, Query & planning, closing CI-02's retrieval-surface gap and specifying the hot-path envelope store) — without re-running the count. Shipping a stale count in the same document that declares the budget is exactly the failure this gate exists to prevent, one level up, and is corrected here rather than left for a reader to catch. (An `EntitlementSnapshot` type is deliberately *not* added to this count: staleness is specified as fields on the existing evaluation context an `Operator` already receives, not a new named type — a scope call made explicitly to avoid growing the count further while fixing it.) The budget is set at **40** — real headroom of **5** over the corrected count of 35, not 9. Phase 1's own additions are pre-declared against that headroom now, not discovered later: `EntitlementPredicate`, `RoleBinding`, and `KeyScope` (the fine-grained-ACL and per-record-crypto-shred types Phase 1 already commits to building) consume 3 of the 5, leaving **2** of headroom for anything genuinely unanticipated once Phase 1 ships — uncomfortably tight, stated as such, and flagged in §Open questions rather than smoothed over. The "delete one to add one" rule activates only once the budget itself — not the current count — would be exceeded. A pre-committed exception is a mechanism; a discovered one is exactly the churn axiom 8 exists to forbid, and this revision closes that gap by pre-committing rather than by flagging it as future work.

**Security hardening as an unconditional default versus an opt-in bundle — a pattern this document was itself repeating one layer up from where it diagnoses it, partially fixed here.** `GovernedProfile`'s refuse-to-start gate and `no_egress` constraint were originally both opt-in, gated behind `security_profile=profile` rather than `Corpus.open()`'s unconditional default — reproducing, inside Datum, exactly the "vendor documents the hazard and ships the workaround instead of the fix" pattern CI-23 and CI-27 name in the incumbent ecosystem. Authorization and budget enforcement were never part of this problem — `principal`/`policy`/`budget` are non-optional compile inputs regardless of `GovernedProfile` (axiom 4) — but the audit/egress/guardrail bundle was. The fix adopted here: **audit-trail logging is no longer part of the opt-in bundle.** Every `Plan` execution already emits a persisted, replayable trace by default (§Core abstractions #5, §Subsystems Evaluation & observability) — this was already true and is now named explicitly as the audit default, closing that specific piece of the pattern without inventing new machinery. What remains opt-in, and is named as a deliberate, not accidental, scope boundary: the *formal* `GovernedProfile` declaration-and-refusal engine (below) and `no_egress` specifically, both deferred to Phase 1 as machinery to build, per §MVP definition — not because default-safe egress and start-time refusal are undesirable, but because "required controls" does not yet have a definition credible and tested enough to hard-refuse a deployment over.

```python
profile = GovernedProfile(require=["authorization", "audit_trail", "no_egress"])
corpus = Corpus.open("s3://acme/knowledge", security_profile=profile)
# Corpus.open() raises ProfileViolation and refuses to start if any required
# control is absent — CI-23's fix shipped as a hard gate, not a hazard
# documented next to its own workaround. audit_trail is listed here for
# completeness but is redundant with the kernel's own unconditional default
# (above) — GovernedProfile's remaining marginal value is no_egress and the
# refusal ceremony itself, both Phase 1.
```

**Failure handling.** A "governed" deployment profile refuses to start without required controls (authorization, audit, egress policy) declared, rather than shipping with a workaround documented next to the hazard — Phase 1, per above. Crypto-shred forgetting's single point of failure — the key management system — is named explicitly, not footnoted: a KMS hardening requirement (envelope encryption, key rotation, scoped blast radius per policy scope) is a stated dependency of shipping `forget(mode="crypto_shred")` at all, and is exactly why that mode is Phase 1, not MVP (§MVP definition) — no v1 deployment depends on a KMS this design has not yet specified hardening for. A pre-shred timing race (content already cached or exported by a downstream consumer before the shred completes) is named as a residual risk the completion proof does not close, and remains a Phase 1 risk to close alongside the KMS design itself, not a v1 concern.

## Issue-coverage traceability

Graded against each issue's *restated* definition and testable acceptance criterion in `common-issues.md`, not its headline name. `Tax. verdict` carries the taxonomy's own adversarial-verification result — **confirmed**, **weakened** (restated in place), or **unverified** (CI-13, CI-14, CI-15–27 were not adversarially verified; designed against a compiled, not re-confirmed, requirement). `Solved` = the architecture implements the rewritten acceptance test by construction. `Mitigated` = a real, partial mechanism exists but the full acceptance test depends on work outside a retrieval framework's reach (identity platforms, model training, ecosystem-wide vendor adoption, or genuinely open research). `Unaddressed` = out of scope.

**A note on how this table changed in revision, stated here rather than only in the changelog.** An independent re-check of this document against its own subsystem text (not against a competing framework) found five rows graded more generously than the mechanism actually specified supported — always in the same direction, toward the higher grade, which is itself the CI-15 self-grading pattern this document warns about elsewhere. CI-02, CI-06, CI-09, CI-11, and CI-14 are downgraded below from an earlier `Solved` to `Mitigated`, with the reason named in each row rather than smoothed over. Two of the five (CI-02, CI-11) also received a *mechanism* fix in this revision, not merely a lower grade — the grade came down anyway, because the original `Solved` was awarded before the fix existed, and holding the higher grade after patching the gap the audit found would repeat the same pattern in the other direction.

| CI | Restated claim (short) | Tax. verdict | Design verdict | Mechanism |
|---|---|---|---|---|

## Anti-scope

Everything below is a considered exclusion — including one deliberate, partial rejection of the winning skeleton's own proposal — not an oversight.

- **No agent loop, orchestrator, or scheduler.** LangGraph, the Claude Agent SDK, CrewAI, or a bespoke loop own it. `SearcherShim` is a reference default policy for weak models, not a mandatory executor.
- **CAL (the internal plan-compilation language) is never a mandatory agent-facing surface.** This is a deliberate, partial rejection of the systems-db skeleton's own proposal, made explicitly rather than quietly: the eight verbs in §Core abstractions #7 are the only interface any model or shim is required to learn; CAL exists purely as optional expert plumbing for callers who want to write an explicit plan, closing the "new DSL is a real adoption tax" objection multiple judges raised.
- **No generation-time prompt-templating engine.** Removes CI-13's dominant CVE class (RAGFlow's Jinja2 RCE, Haystack's PromptBuilder RCE) by non-existence, not by hardening it.
- **No visual DAG/pipeline builder.** The single most CVE-dense cohort in the taxonomy (Langflow's CISA-KEV RCE) exists because that cohort ships user-authored code nodes as a feature; Datum has no such surface.
- **No proprietary vector index, embedding model, LLM, or parser.** Index-agnostic and model-agnostic by design; conformance suites are the interoperability contract, not a competing product.
- **No mandatory graph engine in core.** Graph is one optional, off-by-default `Operator` — GraphRAG-Bench found graphs "frequently underperform vanilla RAG" on fact retrieval at 40–60× the index cost; shipping one as a founding abstraction would repeat that mistake inside a framework built to avoid it.
- **No memory *product*.** No extraction heuristics, no consolidation judgment calls shipped as defaults, no forgetting-policy UX. The write-path *primitives* underneath such a product are kernel (§Subsystems, Memory & mutation); the product decisions are pluggable and off unless a deployment opts in.
- **No in-house identity/ACL-sync machinery.** `principal`/`policy` are typed and enforced; mirroring Okta/AD/OpenFGA group membership (Glean's User Store, Q Business's identity crawler) is connector-side integration work Datum enables but does not perform.
- **No cryptographic PIR/HE retrieval by default.** Priced at 4–190× per-query overhead with no support for adaptive multi-hop queries — incompatible with an agent loop by construction. A TEE-backed elevated-privacy tier (<10% overhead) is the default for deployments that need more than partition-plus-predicate; PIR/HE remain opt-in for single-shot, latency-insensitive queries only.
- **No standalone hallucination-detection or guardrails product — and, stated explicitly rather than left implicit, no consumer for the out-of-band evidentiary envelope either.** `EvidenceState`'s typed provenance and sufficiency fields, and the `hit_id`-keyed `HitRegistry` entries behind them (§Subsystems, Evidence & trust), are collected by Datum and resolved by Datum, but *acted on* by nobody Datum ships: a guardrail that reads `trust_class` before allowing a citation, a disambiguation UI that surfaces `conflicts`, a hallucination detector keyed on `verdict` — all of these are the actual enforcement step, and all of them are BYO. This is named here, not just in §Research contributions #5, because it is exactly the kind of scope boundary that is easy to let a "closes the gap" headline obscure; stating it as an anti-scope item is the more honest home for it than a footnote.
- **No universal multi-modal parser or OCR research.** Best-of-breed parsers plug in behind the canonical-IR interface; Datum does not attempt to beat OHR-Bench's ceiling.
- **No hosted managed tier gating core security, eval, or lifecycle features.** Authorization, the conformance suite, the eval loop, and erasure are core-tier, non-negotiable, and paywalling any of them would reproduce the exact open-core root cause the taxonomy names for CI-01, CI-05, CI-06, and CI-08.
- **No multilingual-first design and no resource-governed ingestion runtime in v1.** Named explicitly (CI-22, CI-19) rather than silently ignored.
- **No model training.** Datum consumes trained policies (frontier or the shipped `SearcherShim`); it does not run RLVR pipelines or curate SFT data.
- **No bundled dashboard or visualization product.** The operator console described in §Subsystems, Learning & adaptation, is a specified interaction contract (plain-language promotion/rollback notifications, a pin/kill switch) — not a shipped web application a deployment is required to run.
- **No mandate on programming language or runtime.** Every layer's interface is a typed contract, not a language binding; the Python sketches throughout are illustrative, matching the convention every source proposal used, not a commitment that the reference implementation must be Python.

## Adoption path

**Phase A — bridge, don't replace, corrected.** The original version of this phase claimed a failing conformance run was merely "diagnostic" while implying the store still bridges in cleanly; on inspection that was self-blocking on this document's own terms, and is replaced here with the mechanism that actually works. Register an existing vector store (Pinecone, Qdrant, a Bedrock KB, pgvector) as an `Operator` and run it against the conformance suite. Two outcomes, and CI-03's own confirmed evidence says the second is the common one, not the exception:

- **Passes** (filter algebra, score contract, tenancy fail-closed, entitlement-staleness) — genuinely uncommon for an existing metadata-filter-ACL store, precisely because CI-03 confirms most of them fail this class by construction. If it passes, it registers as an ordinary conformant `Operator`.
- **Fails** — the store still registers, but as a declared `non_conformant` `Operator` carrying a machine-readable capability manifest naming exactly which test classes it failed. The Plan Compiler refuses to route any ACL-bearing plan fragment to a `non_conformant` operator — fail-closed is preserved by routing around the gap, not by trusting a store that already demonstrated it can't be trusted — while relevance-only fragments (no security-relevant predicate in play) may still use it, and every `EXPLAIN` surfaces the declaration plainly rather than silently.

**What this phase actually buys, corrected from the original overclaim.** A wrapped foreign index — conformant or not — gives a typed, budgeted call shape at the plan layer. It does **not** give `Record`s, a `ProvenanceCapsule`, or lineage: axiom 2 requires every derived artifact to be a materialized view over the canonical L2 Ground Store, and a foreign index's internal state was never derived from Datum's own L2 — there is nothing for `LineageManifest` to point at. Provenance and lineage require ingesting through Datum's own write path, which is Phase D, not Phase A. This is a narrower claim than "buys typed IR and provenance without ripping out an existing index," and the narrower claim is the one this document now makes.

**Phase B — swap the tool surface, keep the loop.** Stand up the MCP server exposing the five read verbs behind the existing agent loop (LangGraph, CrewAI, a custom ReAct loop, the Claude Agent SDK) unchanged — Datum does not compete with any of these for loop ownership. The MCP tool schema follows Anthropic's own tool-design guidance directly: consolidated (not a raw store wrapper), token-efficient with a response-detail enum, semantically identified rather than opaque, matching the shape models are already RL'd to trust.

**Phase C — turn on measurement before touching anything else.** Bootstrap the zero-label golden set against the existing corpus and gate any subsequent config change against it. This produces a regression signal for free, before any further migration step, which is deliberately the *first* payoff a team sees rather than the last.

**Phase D — migrate the write path incrementally.** For agent memory specifically, start by wrapping an existing store (Mem0, Letta) with admission control and `trust_class` tagging rather than a rip-and-replace; move to the native `WriteOp` algebra only when idempotency and transactional supersession become the actual blocking issue, not on a fixed schedule.

**Phase E — enable learning last.** Turn on the promotion-gate loop only after tracing and the golden set have accumulated real, debiased production signal — activating a learning loop before the safety infrastructure that catches a bad promotion exists is precisely the failure mode Self-RAG's and CRAG's unaudited-at-ship-time controllers fell into.

**Interop.** Every physical operator, every embedder, every parser, every LLM is a versioned, swappable dependency referenced by `source_version` in the provenance capsule — never vendored. Nothing about the architecture requires a single-vendor deployment; the conformance suite is precisely the mechanism that makes a mixed-vendor deployment safe rather than a leap of faith.

**Why this order, specifically.** Each phase is sequenced so a team gets a measurable win before taking on the next phase's risk: Phase A buys a typed, budgeted call shape without a migration — not provenance or lineage, corrected above; Phase C buys a regression signal *before* Phase D's write-path changes make regressions possible to introduce in the first place; Phase E is last because it is the only phase that adds a genuinely new class of failure (a learning system's own feedback-channel attack surface) rather than merely closing an existing one. A team that stops after Phase C has closed CI-01 and CI-09 relative to its starting stack, and made CI-03's status *typed and visible* rather than silent — closed outright only if its wrapped store happens to pass conformance, which is the less common case. CI-02's write-time precondition mechanism is not active for a Phase-A/B/C-only deployment, since ingestion hasn't moved to `DocumentPolicy` yet — that is Phase D's payoff, not Phase C's, and this is a correction from an earlier, looser claim. Stopping partway is still a supported end state, not a failure of the migration — the corrective to the over-abstraction trap (a framework that demands full adoption to pay off at all) named throughout the taxonomy's own causal map — it is simply a smaller, more precisely bounded win than "stops after Phase C" originally claimed.

Buildable today with zero dependency on unbuilt research, combining the most conservative feasibility scoping across all five source proposals. **This section is substantially leaner than an earlier draft** — a feasibility critique found the original MVP definition a serial nine-layer build no 2-3-person team ships in a quarter, and eight specific items below are cut relative to that draft, each named at the point it's cut and again in §Revision changelog. Two of the eight were reconsidered rather than simply removed, on a specific technical ground stated inline, and kept.

- **Ground Store**: Postgres (metadata/WAL) + object storage (blobs), one structural parser (Docling-class), content-addressed `Record` with bitemporal *columns*. **Cut:** the bitemporal *query* surface (as-of/valid-time reads — "what was true as of date X") is deferred to Phase 1; no v1 deployment needs point-in-time reconstruction, and building the columns now without the query machinery avoids a later one-way-door migration at near-zero cost. **Cut:** crypto-shred forgetting, at *any* key granularity, is deferred to Phase 1 in full — v1 ships `tombstone` only. An earlier draft shipped crypto-shred at per-policy-scope granularity as a "shippable simplification," but that still pulls in a KMS dependency (envelope encryption, rotation, blast radius) for a guarantee an MVP adopter's own downstream consumers can't yet rely on either; deferring the entire mode, not just its granularity, removes a KMS dependency from v1 altogether.
- **Write path**: three `WriteOp`s (`assert_`, `supersede`, `forget[tombstone]` only at v1); `invalidate` and full `consolidate` policy surface deferred. `DocumentPolicy` ships. **Cut:** `ConversationPolicy` is deferred to Phase 1 in full, not merely gated off by default — building and testing a policy this design's own Adoption Path (Phase D) says to defer until "idempotency and transactional supersession become the actual blocking issue" contradicted that same advice applied to this project's own build order, and this revision applies it.
- **Derivation**: content-defined chunking (FastCDC, §Subsystems Ingestion & derivation) as the default chunk View from day one, boundary-constrained against the structural IR per the mechanism specified there; two Views — BM25 lexical and one dense embedder.
- **Physical operators**: grep, BM25, and one ANN engine (a DiskANN-lineage or IVF+RaBitQ engine via an existing embedded library) — no graph, no late-interaction yet, each already passing the conformance suite (including the entitlement-staleness fail-closed case) before registration, because the suite is cheap to write even when the operator roster is small.
- **Plan Compiler**: the `Plan`/EXPLAIN representation is correct from day one; plan-selection ships as a **declared, dated rule-table policy — zero learned or cost-based components**, consuming only static, declared configuration, not a live-statistics feed (§Subsystems, Query & planning). This is the single most important MVP-scoping decision in this document: shipping the interface commitment (a slot exists, EXPLAIN/replay work) without waiting on the optimizer research to mature. **Kept, on reconsideration:** `since(version, principal)` ships in the frozen v1 read surface after all — an earlier feasibility pass proposed cutting it as dependent on the bitemporal query machinery just deferred above, but `since()` is answerable directly from the L1 WAL tail (already ordered by transaction time) without valid-time reconstruction; it is a changefeed, not a point-in-time query, and is cheap. What's genuinely deferred is the heavier as-of capability, not this verb — cutting a verb from the frozen surface and potentially having to restore it later would itself be exactly the kind of interface churn axiom 8 exists to forbid, so this revision checked the dependency rather than cutting on the critique's first-pass assumption. The obvious follow-up objection — doesn't filtering a changefeed by caller entitlement need the same predicate machinery being deferred? — doesn't bind at v1 specifically because ACL is namespace-partition-only at v1 (below): filtering `since()`'s WAL tail by the caller's namespace is a cheap equality check on a partition key, not a predicate evaluation; the fine-grained residue that would make changefeed filtering expensive is exactly the part deferred to Phase 1 alongside `since()`'s own as-of sibling.
- **Principal/policy/budget**: enforced from v1 — cheap, a type-system and admission-control decision, not a modeling one. ACL ships as namespace partitioning on the tenant/department dimension only; the fine-grained conformance-tested-predicate path (and its entitlement-staleness fail-closed test) is Phase 1.
- **EvidenceState**: an explicitly *uncalibrated-but-typed* sufficiency score, labeled as such rather than mis-claimed as calibrated; `EvidenceItem`'s structural fields (`section_path`/`page`/`bbox`) are populated from day one since `Record.body.StructuredBody` already carries them — this is a cheap propagation, not a modeling task, and shipping it at v1 is what §Issue-coverage traceability's CI-02 row now credits.
- **Eval**: **cut and replaced.** A small, fixed, human-curated regression set (tens to low-hundreds of query/expected-evidence pairs) gates any manual config change at v1, in place of the zero-label, corpus-derived golden-set bootstrap (Chroma-style) an earlier draft specified for day one — generating a good synthetic golden set from an arbitrary corpus is itself a research-adjacent problem, not the cheap measurement-first win the original framing implied, and is deferred to Phase 1 alongside the promotion-gate machinery it feeds. **No promotion-gate machinery yet** — learned-policy's own phasing recommendation, judge-endorsed: ship pure measurement before any learned component, so there is no learned behavior to audit before the audit infrastructure exists.
- **Agent Tool Surface**: the five read verbs (including `since()`, per above), shipped as an MCP server, tested directly against real tool-calling models rather than assumed correct from the type signature alone.
- **Security default**: audit-trail logging (the persisted Plan trace) ships unconditionally, as it always was underneath `EXPLAIN`/replay — not gated behind `GovernedProfile`. **Cut:** the formal `GovernedProfile` declaration-and-refusal engine and `no_egress` enforcement are deferred to Phase 1 (§Subsystems, Security & governance) — "required controls" does not yet have a definition tested enough to hard-refuse a deployment over, and shipping the ceremony before that definition is credible would be governance theater, not governance.

**What stays deferred, gathered in one place.** Bitemporal as-of query machinery; crypto-shred at any granularity; `ConversationPolicy`; the generative golden-set bootstrap and the promotion-gate loop it feeds; the formal `GovernedProfile` refusal ceremony and `no_egress`; per-record crypto-shred key granularity and KMS hardening; the multi-backend conformance matrix beyond one vendor per operator kind. Every item on this list is buildable, none is blocked on unmature research, and all are sequenced below rather than dropped.

**Phase 1 (next).** Bitemporal as-of query surface; multi-backend conformance suite extended to ≥3 real store vendors; the fine-grained predicate ACL path plus continuously measured low-privilege recall and its entitlement-staleness fail-closed test; dual-read embedder migration; `ConversationPolicy`; crypto-shred forgetting (per-record granularity from the start, not per-policy-scope, since there is no installed base yet to migrate off a coarser grant) with a hardened KMS design (envelope encryption, rotation, scoped blast radius) — the key-scope-granularity choice is itself a one-way door and is made deliberately here rather than inherited from an MVP shortcut; the `GovernedProfile` formal refusal engine and `no_egress`; the Chroma-style generative golden-set bootstrap, replacing the fixed regression set once it is validated against it, not instead of it.

**Phase 2.** The promotion-gate loop goes live for exactly two slots first — stop/abstain and fusion weights, following learned-policy's own smallest-falsifiable-slice recommendation — with IPS/AIPW debiasing, always-valid sequential testing, and canary/rollback, before any other slot is touched. This is also the phase where replay-by-record's logged propensity stops being the trivial constant-1.0 case (§Core abstractions #5) and starts carrying real debiasing weight.

**Phase 3.** `SearcherShim` moves from lightly-prompted to actually trained (the s3 recipe); third-party vendors publishing their own conformance-suite results against Datum's public suite — named honestly as a coordination problem, not an engineering one, that the framework can only make possible, not compel.

## Evaluation plan

**Substrate-correctness benchmarks.** The conformance suite (filter algebra, score contract, tenancy fail-closed cases, entitlement-staleness fail-closed) as a pass/fail CI gate across every registered operator — a mistranslating backend cannot merge. The **kill-the-vendor drill**, run literally: delete Datum's own binaries; using only the exported Ground Store and View manifests, have a third party rebuild a recall-equivalent system from scratch; recall parity on a held-out golden set is the pass condition. An erasure probe: `forget()` → zero retrievable content across index/cache/replica within a declared SLA, on a soak test large enough to also surface tombstone-driven recall decay.

**Performance/scale benchmark — named as unbuilt, not left absent from the list.** This project's own taxonomy names p99-latency-under-concurrent-ingest-and-filtered-query, measured at a declared recall target, as the single largest measurement gap in the survey (CI-21) — and an earlier draft of this evaluation plan simply didn't list it alongside the benchmarks it does specify. It is specified here as a harness this design commits to building, not one it claims results from yet: hold ingestion throughput fixed at a stated rate (documents/sec) while driving concurrent filtered queries at increasing QPS, and report p50/p95/p99 latency and realized recall (not just nominal recall) at each load point, across the HitRegistry/trace-write/ACL-predicate hot-path components §Subsystems, Query & planning, costs individually. Naming the harness is free; running it and publishing the numbers is Phase 1 work, and this document does not claim otherwise.

**Retrieval-quality benchmarks.** BEIR/MIRACL for baseline lexical/dense quality; LIMIT (arXiv:2508.21038) run explicitly to characterize *where* the dense channel's combinatorial ceiling binds, published in the manifest's own coverage metadata rather than discovered in production; BRIGHT for reasoning-mediated relevance.

**Sufficiency/abstention benchmarks.** EnterpriseRAG-Bench (arXiv:2605.05253) — explicitly the credible, ~500K-document benchmark with a dedicated absent-information category, disambiguated per the taxonomy's own correction from the discredited five-question `retrievalci` anecdote — measuring the fraction of unanswerable questions on which `insufficient_evidence` fires correctly, against a baseline established on the identical harness, not assumed at 0% without measurement.

**Adversarial suites.** PoisonedRAG and AgentPoison as pre-deployment gates; a salience-induction suite reporting residual attack success honestly (a non-zero residual is the expected, documented result, not a failure of this evaluation); AgentDojo for the CaMeL-class utility-tax boundary this design composes with but does not itself build.

**Agentic-loop benchmarks — the dual-consumer falsification test.** GAIA/BrowseComp-class tasks run three ways on the same corpus: (a) a frontier policy calling the eight verbs directly, (b) `SearcherShim` driving a weak/local model, (c) a hand-wired baseline pipeline (LangChain- or LlamaIndex-style), measuring task success, token cost, and latency. **Falsification criterion:** the dual-consumer claim in axiom 8 is wrong, not merely disappointing, if (a) shows a measurable scaffolding tax versus a bespoke integration, or if (b) fails to close a meaningful fraction of the gap to (a) for the same weak model.

**Learning-loop ablations.** Frozen-default vs. shadow-learned over time on the same corpus and traffic — a null result falsifies the promotion loop's value for that traffic regime, not merely disappoints it. IPS-debiased vs. naive-click reward, replicating the click-model literature's known warning on Datum's own logs. Independent-auditor replication: hand a third party only the logged trace, the golden set, and a promotion decision, and ask them to reproduce the promote/hold verdict from that artifact alone.

**Production metrics, tracked continuously.** Recall/nDCG per dated profile over time, with regression alarms wired to the golden set; cost-per-resolved-query and the fraction of billed tokens attributable to a named stage (≥95% target); conformance-suite pass rate across all registered backends, as a first-class release metric, not a one-time audit; **low-privilege recall**, published continuously on both the partition and predicate ACL paths; promotion frequency and post-promotion regression rate; escalation-rate correlation with downstream error.

**Eval-crisis-aware methodology.** Judges are calibrated against a human-anchored slice with PPI-style confidence intervals before gating anything, precomputing CI-15's self-collision rather than discovering it after the golden set is already load-bearing. Benchmarks are pinned to a content-hashed manifest, not a library version, so a claimed result is reproducible by construction. Every claim in this evaluation plan that depends on research not yet mature (calibrated cross-corpus sufficiency, a validated marginal-value-of-next-call estimator, provable structural instruction/data separation) is named as such in §Open questions rather than asserted as already solved.

## Research contributions

Numbered as claims a paper built on this design would need to defend, each traceable to a specific graft-and-resolution in §Design axioms rather than to the winning skeleton alone. **This section was rewritten wholesale in this revision.** An earlier draft numbered these as if novelty were the default and prior art the exception; an external check reversed that assumption for six of the eight and found one internal contradiction in a seventh. Each entry below now opens with the honest verdict — **exists**, **partially-novel**, or **synthesis** (a specific combination of named prior-art pieces that, as far as this project's search found, has no single existing precedent) — followed by the named prior art, followed by what residual claim, if any, survives it. None of the entries below claims to invent a mechanism from nothing; §Limitations & honest tradeoffs names the two or three places this document thinks the *synthesis itself*, not any mechanism inside it, is the strongest candidate for "genuinely combined nowhere else."

1. **[Partially-novel] The diagnostic synthesis is real; the mechanism it's built from is not.** Four of the taxonomy's confirmed defects (CI-03, CI-05, CI-07, CI-08) collapsing to one missing primitive — a compiled logical/physical retrieval plan — is genuine synthesis work, verified by the exact axiom-to-issue mapping in §Design axioms. The System-R-style split that closes them is not this document's invention: LOTUS (Stanford/Berkeley) and Palimpzest (MIT CSAIL, arXiv:2405.14696) already ship a declarative logical layer with a real logical/physical optimizer over general AI-data workloads. What is specific to Datum, and what this contribution should actually be understood to claim, is narrower: which four RAG-specific, adversarially-confirmed defects the split closes, and the specialization to typed `principal`/`policy`/`budget` compile inputs and fail-closed-by-type ACL predicates that a general-purpose optimizer over structured-plus-unstructured data was never built to provide.
2. **[Partially-novel] An engineering discipline, not a new abstraction.** Treating plan-selection as a versioned policy in a slot — ship a rule table now, earn a smarter policy later without touching the interface — is a legitimate, load-bearing discipline for avoiding both CI-14's frozen-heuristic disease and an unbuilt cost-based optimizer's vaporware trap. The shape itself is ordinary: Palimpzest's optimizer already picks among concrete logical/physical programs by estimated cost/time/quality at runtime; arXiv:2602.17914's learned filtered-ANN planner already swaps strategy per query from live statistics; pluggable, GUC-tunable query planners are standard RDBMS practice (Postgres cost parameters, SQL Server plan hints). The residual claim is organizational, not technical: applying that ordinary shape to a slot most RAG frameworks never built at all, with the "declared rule table today, feedback-floor-gated challenger tomorrow" discipline stated as an explicit contract rather than an incidental implementation choice.
3. **[Exists] Replay-by-record is a named, decades-old idea, correctly transposed.** Reconstructing a persisted trace — realized action, logged propensity, exact policy version — instead of recomputing against a live policy is the "Replay Method" from contextual-bandit off-policy evaluation (Li, Chu, Langford & Wang, WSDM 2011), and it is the identical idea Temporal.io implements as durable execution (an Event History replayed against workflow code, with a separate, explicitly-named mechanism to run new code against old history). This document's contribution is the transposition to a retrieval Plan IR specifically, including the honest consequence that the logged propensity is a trivial constant until Phase 2 installs a stochastic policy (§Core abstractions #5) — not the reconciliation idea itself, which predates this document by fifteen years.
4. **[Synthesis — the strongest candidate in this list] Fusing two halves that each already exist separately, under one kernel neither original system spans.** TOKI (arXiv:2606.06240) already formalizes a bitemporal operator algebra for LLM-agent memory specifically; Databricks Vector Search's Delta Sync Index already gives documents a WAL-backed, incrementally-maintained derived-index story specifically. Neither spans both source classes. Putting both through one literal shared write kernel (`WriteOp`), with pluggable per-source `WritePolicy`, while keeping the write *policies* — parse/supersede for documents, extract/consolidate for conversation — genuinely distinct, is a real, if modest, engineering synthesis: no system found in this project's search does this, though every individual half of it is established. This is the contribution in this list this document would defend most confidently as "not found elsewhere," precisely because it claims the least on its own (a fusion, not a mechanism).
5. **[Exists, and this document previously overclaimed it — corrected here] Raises attacker cost; does not close the gap, and no wording in this document now says otherwise.** An out-of-band evidentiary envelope — authority/trust/provenance never re-serialized into the tokens a model attends to, resolved only through an opaque `hit_id` — already ships in LlamaIndex's Index v2 legal-kb (July 2026) and is independently generalized as a named, general agent-safety pattern in arXiv:2605.29082. An earlier draft of this document's own header for this contribution said the mechanism "closes" the salience-induction/content-innocent-attack gap, while §Subsystems, Evidence & trust said plainly, in the same document, that no content-inspection defense reaches this class — an internal contradiction independent of the external prior art. Both are fixed in this revision: the header now says "raises the cost of," matching the subsystem text, and the external prior art is named rather than left as an implicit "this is new." What is not resolved by this fix, and is named in §Anti-scope: the mechanism collects enforcement-grade metadata and specifies no consumer for it — every component that would act on `trust_class`/`verdict` is explicitly out of scope.
6. **[Partially-novel] The architecture is standard; the continuous dual-path metric is the plausible sliver.** Namespace-per-tenant plus row/document-level predicate filtering is standard enterprise-search and multi-tenant-database practice — Glean indexes with ACLs at both index and query time; Pinecone namespaces plus metadata filters, Postgres schema-per-tenant plus row-level security, and ES/OpenSearch index-per-tenant plus document-level security are the same two-tier pattern already in wide production use, and this project's own corpus (the LangChain4j #2513 / Spring AI #3577 incidents) is itself evidence that predicate-only ACL is a known, worked problem in this space, not an undiscovered one. What this project's search did not find under any name: **low-privilege recall published as a continuous, first-class metric on both paths simultaneously**, as the specific mechanism that catches silent starvation on whichever path is degrading. That measurement discipline — not the partition-plus-predicate architecture underneath it — is the residual claim, and it is a monitoring-practice addition to an existing architecture, not a new architecture.
7. **[Exists] An import, correctly labeled as one, applied to a new object.** Champion/challenger testing with canary rollout and automatic rollback is standard, named MLOps practice (ModelOp's glossary, MLflow's model-lifecycle tooling); IPS/AIPW-debiased off-policy evaluation and always-valid sequential testing are, in this project's own words elsewhere in the corpus, "decades-settled in search ranking" — `research/02-frameworks/cross-cutting-gaps.md`'s own line, written before this document, states "RAG must re-import the online-learning discipline classical search never lost." Nothing here is a new mechanism, and this document does not claim one. The contribution is entirely in the choice of object — RAG's plan-compiler decision points specifically — and in the per-decision-point feedback-floor taxonomy (stop/abstain ~10²–10³, fusion weights ~10³–10⁴, etc.) as a scoping exercise, which is reasonable and useful but is exactly that: a scoping exercise, not a technique.
8. **[Partially-novel] An established genre of artifact, applied to a new kind of requirement list.** Grading a system's claimed conformance against a verified, independently-sourced requirement list is standard practice in safety-critical and compliance engineering — DO-178C traceability matrices, SOC2/ISO control-mapping tables, NIST 800-53 control-assessment worksheets are the same genre. "Prior art" here means an established artifact type, not a competing system. Applying that genre to grade a RAG framework's design against an adversarially-verified defect taxonomy — rather than a regulatory control list — is a legitimate, modest transposition; the traceability-matrix-against-independently-verified-requirements idea itself is old, and the self-grading discipline this document tries to hold itself to in §Issue-coverage traceability (documented in this revision's own tally correction) is the part worth taking seriously, not the artifact format.

## Open questions

- Does the plan-selection policy's declared cost/coverage/scoring-family metadata actually change routing behavior when measured, or is it descriptive metadata nobody's policy conditions on?
- Do trained tool-use policies actually extend grep/bash-level trust to a small-but-new eight-verb surface, or is model trust specific to the literal tools they were RL'd against?
- Can partition-plus-predicate ACL actually bound post-filter starvation for realistic enterprise entitlement lattices (role × region × trial × tier), or does the fan-out still explode in practice for the coarse dimension too?
- Does crypto-shred-at-the-key-layer survive a real KMS hardening audit, and what is the actual blast radius of a KMS failure in production — this is treated as a load-bearing risk, not a footnote, precisely because all three judge lenses flagged it independently, and it is why this revision moved the whole mode to Phase 1 rather than shipping any granularity of it at MVP.
- Does a declared `max_staleness` SLA on an entitlement snapshot (§Core abstractions #4) actually get set conservatively in practice, or does operational pressure push the threshold up until the fail-closed gate rarely fires — turning a mechanism meant to catch silent ACL-freshness collapse into exactly the measurement theater CI-15 warns against elsewhere in this document?
- The kernel symbol budget is now a stated number (40, corrected count 35 after this same revision's own additions were recounted, §Subsystems Security & governance) with Phase 1's own additions pre-declared against it, leaving 2 symbols of headroom once Phase 1 ships. Is that enough for everything Phase 2 will actually need, or will this document be back here in a year having the same collision the original, unbudgeted version of this gate already had once, just at a higher number and a tighter margin?
- Is the closed decision-point list (fusion weights, rerank depth, stop/abstain, representation routing, enrichment admission) the right partition of "what's worth teaching to learn," or does a further decision point — embedding-model selection itself, distinct from the routing choices already listed — need first-class status?
- Does the self-bootstrapping golden set avoid becoming its own CI-15 measurement theater — an uncalibrated judge grading a golden set drawn from the same corpus it is judging — under sustained production pressure to look cheap or look rigorous?
- Where does the device/non-device regulatory line fall for a multi-step agentic system built on this substrate in regulated verticals (medical, legal)? Datum supplies the primitives a determination would need (provenance depth, abstention, audit trail) but does not itself settle where the line falls.
- Can verified erasure ever extend to policy weights derived from an erased or superseded record — not just the index — without full retraining, and is that even the right bar to hold a retrieval substrate to?
- Does `authority_tier`, where a registry genuinely exists, measurably change downstream answer safety in a general enterprise deployment, beyond the single medical-vertical ablation the mechanism is generalized from?
- Can this project's own governance — the semver pledge, the symbol-diff gate — survive the open-core economics that hollowed out every predecessor's *stated* discipline? A design document can specify a mechanism; it cannot pre-commit an organization to funding it, and CI-08's own root cause is named as an economic/governance problem, not a technical one, that this document answers only with a technical CI gate. The most credible *non-binding* answer this document can point to without pretending to have built it: foundation-style stewardship (an Apache Software Foundation-class donation, or a dedicated non-profit holding the trademark and the semver pledge as a governance document a commercial vendor cannot unilaterally revoke) is the closest existing precedent for keeping a core technical commitment outside the reach of a single company's funding cycle — named here as a recommendation for whoever builds this, not as something this document has arranged.
- What is the right unit for the kernel's semver pledge once axiom 7's promotion loop is live — the whole nine-layer stack, or each layer independently — given that the Plan Compiler's *behavior* changes over time (a new champion policy) even while its *interface* stays frozen? A stability pledge that only covers signatures and silently allows behavior to drift may not be the guarantee CI-08 was actually asking for.
- Does `navigate`'s late-bound-granularity affordance (structure-first browsing with no text materialized until `fetch`) earn its keep in practice, or do most callers — frontier and weak-model alike — simply call `search` and never use it, making it added surface area with no measured benefit?

## Limitations & honest tradeoffs

This section collects, in one place, what the rest of this document already says piecemeal but does not summarize: what a hostile reviewer would be right to press on, stated by this document itself rather than left for someone else to find first.

**Novelty is concentrated in synthesis, not mechanism, and this document now says so everywhere a claim is made, not just here.** Of the eight numbered claims in §Research contributions, one (#4, the shared `WriteOp` kernel spanning documents and agent memory) is graded a genuine synthesis with no single found precedent; two (#3, #7) are graded existing mechanisms correctly transposed with essentially no residual novelty in the mechanism itself; the remaining five are graded partially-novel, meaning the architecture is standard and a narrower, named piece of the whole (a scoping exercise, a measurement discipline, a diagnostic mapping) is what survives scrutiny. A reader who checks LOTUS, Palimpzest, TOKI, LlamaIndex's legal-kb, or the standard MLOps/enterprise-search literature this document now cites by name will find the same thing this revision's own check found. That is the intended outcome of publishing the check, not a failure of it.

**The most consequential single gap is methodological, not a missing citation.** The research corpus (`research/01-landscape/`, `research/02-frameworks/`) that grounded this design's original novelty claims never surveyed the declarative-optimizer-over-unstructured-data literature — LOTUS, Palimpzest, DocETL are absent from every landscape and framework file this project produced, despite that family being the closest live prior art to this document's own central System-R framing. This is a gap in the research process that produced the corpus, not merely a citation this document forgot to add, and it is named here as the correction most worth making before this design is presented anywhere as filling empty space. §Research contributions #1 and #2 are written to reflect the correction; the underlying research corpus itself is not in this revision's scope to re-run.

**The MVP is roughly half the scope an earlier draft claimed, once a feasibility critique's cuts are applied** (§MVP definition): the bitemporal as-of query surface, crypto-shred forgetting at any granularity, `ConversationPolicy`, the generative golden-set bootstrap, and the formal `GovernedProfile` refusal ceremony are all deferred to Phase 1, not shipped at v1. Two proposed cuts (the bitemporal dependency under `since()`, and the entire replay-by-record trace format) were checked against the actual mechanism and kept rather than cut, on the specific technical grounds stated inline where each is discussed — this document does not treat a feasibility critique as automatically correct any more than it treats its own original scoping as automatically correct.

**This document graded itself more generously than an independent re-check supported, in five specific places, always in the same direction.** CI-02, CI-06, CI-09, CI-11, and CI-14 moved from `Solved` to `Mitigated` in this revision (§Issue-coverage traceability); the corrected tally is 3 solved / 22 mitigated / 2 unaddressed, not the 8/17/2 an earlier draft reported. This is named plainly, with the tally-paragraph rewrite left visible rather than quietly edited, because a design document auditing its own claims and finding they don't hold is a stronger argument for taking its *other* claims seriously than a document that has never been caught overclaiming anything.

**Structural gaps that remain genuinely open even after this revision's fixes, not resolved by any mechanism added here:** entitlement-data freshness is now a typed, fail-closed condition rather than a silent one, but Datum still does not build or sync identity data — a determined attacker who can influence entitlement-sync timing, not just query timing, is not addressed. The KMS dependency for crypto-shred is now entirely Phase 1, which removes it from MVP's risk surface but does not retire it as a future single point of failure. CI-08's economic-survival dependency has a named recommendation (foundation-style stewardship, §Open questions) but no built mechanism — a design document cannot fund an organization. Golden-set/judge circularity is bounded by calibration, not eliminated, for both the fixed MVP set and its Phase 1 generative successor. The feedback-poisoning attack surface a learning system creates (§Subsystems, Learning & adaptation) has a named monitor (`DriftMonitor`), not a proof.

**What would falsify this design, restated plainly rather than left implicit in the Evaluation plan:** the dual-consumer claim (axiom 8) is wrong, not merely disappointing, if a frontier policy shows a measurable scaffolding tax over a bespoke integration, or if `SearcherShim` fails to close a meaningful fraction of the gap for the same weak model (§Evaluation plan). The learning-loop's value is falsified, not just disappointed, by a null result on frozen-default-vs-shadow-learned ablations on real traffic. Stating falsification conditions this directly, rather than only in the evaluation plan's own language, is itself part of the honesty this section is trying to model.
